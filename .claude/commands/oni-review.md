未コミットの diff に対してグーグルシニアエンジニアのズタボロ鬼レビューをかましてください。コードベースを深く広く読むこと。過度に複雑になっていないか、よりシンプルに実装できないか、ロジックの重複がないか、一貫性があるかも考慮。それに対してフラットに妥当性を判断し、対応すべきは対応してください。判断の際にはアプリは MVP 段階という点も踏まえてください。

## レビュー後の TODO 更新

レビューと修正が終わったら、**埋もれると困る残課題を `docs/TODO.md` に追記**すること（無ければ新規作成）。対象は次の2種類:

- **要対応の積み残し**: コードでは消せない手動作業(ダッシュボード設定など)、別 PR に切り出した修正、後追いの検証タスク。
- **「今は直さない」と判断した指摘**: MVP 据え置きにした保守性・一貫性の宿題(なぜ今やらないかの理由ごと)。

書き方のルール:

- **ある程度まとめる**。関連する残課題は小項目を散らさず、1 つの letter 項目(例 `### Z. ...`)にサブ見出し(①②③)でまとめる。索引(冒頭「ステータス一覧」の未完リスト)にも 1 行追加する。
- **必要な文脈を必ず明文化する**。追記時点では作業内容が頭にあるので「○○を共通化」等と省略しがちだが、**後から読んだ人(=未来の自分)にはその文脈が無い**。最低限、各項目に以下を書く:
  - **背景 / なぜこれが残ったか**(どの作業の副産物か、何が問題か)
  - **対象ファイル・関数・シンボル名**(grep で辿れる固有名で)
  - **やること**(具体的な変更内容。「整理」「共通化」だけで終わらせない)
  - **やらない理由(今)**(MVP 据え置きの判断根拠)
  - **参照**(関連する設計書 `docs/design/` / 調査レポート `docs/research/` / memory への相対パス)
- 相対日付は絶対日付に直す(「先日」ではなく `2026-06-21`)。「起票日」を項目名か先頭に入れる。
- 完了済みの指摘や、その場で直した指摘は TODO に書かない(diff / commit message 側の話)。
