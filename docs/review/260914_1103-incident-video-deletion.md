# インシデント記録：保存データが読めないと `Documents/Videos/` の動画を全部消していた（2026-09-14）

## 1. 概要

起動時に `library.json` を読めなかったとき、アプリが**アプリ内に持っている動画ファイルをすべて削除する**状態が
3 日間（2026-09-11 08:00 〜 2026-09-14）続いていた。

```swift
if let library = readLibrary() { load(library) }   // 復号に失敗すると clips は空のまま
removeUnreferencedModels()
removeUnreferencedVideos()                          // 参照＝空集合として Documents/Videos を全削除
```

`readLibrary()` は `try?` であらゆる失敗を nil に潰す。nil のとき `clips` は空のままで、その直後の
`removeUnreferencedVideos()` が「参照されているファイル名の集合」を**空集合**として `Documents/Videos/` を走査するため、
中のファイルを 1 つ残らず消す。

**2026-09-12 に 1 度発火し、過去のスイングが失われている**（§2.3）。そのときは手順の対策（形式を変えたら伝える）で
済ませていて、仕組みとしては塞がれないまま 2 日間残っていた。2026-09-14 の 2 巡目リファクタで塞いだ（§5）。

---

## 2. 影響範囲

### 2.1 消えないもの（確認済み）

- **写真ライブラリの動画（撮影した個人の動画）は 1 本も消えない。**
  アプリのソース全体に `PHAssetChangeRequest` / `deleteAssets` は 1 つも無く、写真ライブラリの資産を削除する経路が存在しない
  （`grep -rn "deleteAssets\|PHAssetChangeRequest" SwingDuet/` → 0 件）。
  2026-09-12 以降、取り込んだ動画は**参照（識別子）**で持つので、クリップの実体は写真ライブラリ側にある
- `Documents/CaptureTakes/`（全体の動画。手元の端末で 8.5 GB）も走査の対象外。`removeUnreferencedVideos` が見るのは
  `Documents/Videos/` だけ
- `library.json` そのものも消えない（読めないまま上書きされるだけ。それも §5 で止めた）

### 2.2 消えうたもの

`Documents/Videos/` にあるアプリ内のコピーだけ。時期で範囲が変わる。

| 期間 | `Documents/Videos/` に何があったか | 失われたときの回復 |
| --- | --- | --- |
| 2026-09-11 08:00 〜 09-12 22:47 | **取り込んだ動画すべて**（当時はコピーで保存していた） | 元動画は写真ライブラリに残るので取り込み直せる。失うのは解析結果・フェーズの手直し・名前・★・位置合わせ |
| 2026-09-12 22:47 以降 | (a) 権限が無いとき OS のピッカー経由で取り込んだコピー<br>(b) 撮影した球のうち、写真ライブラリへ移す前・移すのに失敗したもの | (a) は写真アプリから取り込み直せる。**(b) は回復できない**（アプリ内にしか無い） |

(b) が唯一の「戻せないデータ」で、具体的には撮影中に切り出してから写真ライブラリへ移るまでの数秒間の球と、
権限や容量の都合で写真ライブラリに保存できなかった球。

### 2.3 発火の記録

**2026-09-12 に 1 度発火している。**

`Library.reference` を `syncBasis`（`playback` の中）へ改名したビルドを iPhone に入れた直後、もう一方の worktree
（`swing-duet-atelier`）のセッションが**改名前のビルドを同じ iPhone に上書きインストール**した。
旧ビルドの `Library` は `reference` を**既定値付きの非オプショナル**として持っていて、Swift の合成デコーダは
既定値があってもキーが無ければ例外を投げる。新形式の `library.json` に `reference` が無い → 復号に失敗 → `clips` が空 →
`removeUnreferencedVideos()` が `Documents/Videos/` を全削除、という順で過去のスイングが消えた
（改名は `8b49bc9`。2026-09-12 の作業中に発生し、コミットは同日 14:49）。

当時はまだ全部の動画がアプリ内のコピーだったので、**`Documents/Videos/` の中身は全部消えた**。
元が写真ライブラリにある動画は取り込み直せた（いまの保存データにある 08/30〜09/08 撮影のクリップは、
取り込み日時がすべて 09/11 以降なので、この取り込み直しの分）。取り込み直しで戻らなかったのは
**解析結果・フェーズの手直し・名前・★・位置合わせ**で、これは作り直すしかない。

そのときの対応は、メモリに「形式を変えたら実機に入れる前に必ず伝える」という**手順**を書き残すところまでで、
`ClipStore` の側は変えていない。ユーザーの判断は「MVP なので互換コードは書かない」で、これは形式の互換の話としては妥当だが、
**「読めなかったときに動画を消す」という別の問題が同じ経路に同居していた**ことは、このとき切り分けられていなかった。

露出は 3 日間・29 コミット。

**1 度実害が出たのに 2 日間残った理由**は 3 つある。

1. **問題が「形式の互換性」の話として片付けられた**。実際に起きたことは「形式が合わない ＋ 読めないときに動画を消す」の
   2 つの合成で、後者だけを直せば同じ引き金でもデータは残った。原因を 1 つに丸めたことで、直すべき側が見えなくなった
2. 後片付け自体は「取り込みの途中でアプリが終了したときの残りを消す」ための機能で、**正常系では必ず正しく動く**。
   異常系（壊れた保存データ）を通すテストが 1 件も無く、壊れ方が目に見えなかった
3. コードのコメントが安全側に書かれていた。`ClipStore` の冒頭には
   「読めなければ空の状態から始まり…どれもユーザーに知らせて回復できる種類の失敗ではない」とあり、
   実際には「読めなければ動画を全部消す」だったのに、次に読む人を油断させる記述になっていた

## 4. 発火の条件（どれも現実的だった）

1. **形式を変えたビルドの入れ替え（2026-09-12 に実際に起きた引き金）**。同じ iPhone に本流と atelier のビルドを交互に入れる運用があり、
   新しいビルドが書いた `library.json` を古いビルドが読めなければ発火する。`Clip` に非オプショナルなフィールドを
   1 つ足すだけで成立する（合成デコーダは既定値があってもキーが無ければ例外を投げる）
2. **クリップ 1 本の綻び**。`clips` を 1 つの配列として復号していたので、1 本でも解けなければ全体が読めない
3. **書き込みの途中での終了**。`persist()` は atomic なので原理的には起きにくいが、
   `NaN` を含む値を書こうとして符号化に失敗し続ける経路（§5 で別途修正）があった

---

## 5. 原因

**「データが無い」と「データを読めない」を同じ値（`Library?` の nil）で表し、その値を根拠に破壊的な操作をしていた。**

`removeUnreferencedVideos` は「クリップが参照していないファイル＝孤児」という**導出された集合**を根拠に削除する。
導出の元（`clips`）が信用できない状況があるのに、その区別を型が持っていなかった。

寄与した要因：

- あらゆる復号の失敗を `try?` で 1 つの nil に潰していた（失敗の種類が分からない）
- `clips` の復号が全か無かだった
- `Pairing` など下位の型が寛容でなく、形式変更が即「全体が読めない」になった
- **壊れた保存データを読ませるテストが 1 件も無かった**（正常系の往復テストしか無かった）

## 6. 直したこと

| # | 内容 | 場所 |
| --- | --- | --- |
| 1 | 読み込みの結果を 3 値（初回 / 読めた / 読めない）にし、**読めないときは後片付けを一切しない** | `ClipStore.LibraryLoad` |
| 2 | 読めなかったファイルを `library-<日時>.bak` に**組み替えるより前に**退避する | `ClipStore.backUpLibrary` |
| 3 | 読めなかった回は**保存もしない**（上書きすると次の起動は「読めた」ことになり、そこで後片付けが走って結局消える） | `ClipStore.isReadOnly` |
| 4 | クリップを 1 本ずつ復号し、解けなかった分だけ落とす。1 本でも落ちたら「壊れている」扱いで後片付けを止める | `Library.ClipBox` / `hasUnreadableClips` |
| 5 | `Pairing` に寛容な `init(from:)`。相手の情報が読めなくてもクリップは残す（相手はいつものお手本に落ちる） | `Pairing.init(from:)` / `Clip.init(from:)` |
| 6 | 退避したことをホームの帯で知らせる（「動画は残していますが、この起動では保存しません」） | `SwingListView` |
| 7 | `persist()` の符号化の失敗を握りつぶさない。`NaN` の入口（壊れた動画の長さ）を解析の入口で弾く | `ClipStore.persist` / `SwingAnalyzer.loadVideo` |

テスト（`ClipStoreTests`）：

- 壊れた `library.json` で起動しても `Documents/Videos/` のファイルが残り、退避ファイルができる
- クリップ 1 本が壊れていても他は読め、そのときも動画を片付けない
- 壊れた保存データを上書きしない
- 加えて `PersistenceTests` の往復テストが、**手書きの `init(from:)` にプロパティを足し忘れる**という
  §4-1 の引き金そのものを検出する

## 7. 残るリスクと次の手

1. **この修正が入っていないビルドは、今も同じ動作をする。** 共有 iPhone に atelier のビルドを入れる運用があるので、
   両方の worktree にこの修正が入るまで、形式変更 ＋ 入れ替えの組み合わせは避ける
2. **「参照されていないから消す」という設計自体は残っている。** 導出した集合を根拠にユーザーのデータを消す形なので、
   孤児をすぐ消さず一定期間ゴミ箱に置く方が安全（[TODO.md](../TODO.md) AB）
3. 撮影した球が「アプリ内にしか無い」時間帯（写真ライブラリへ移すまでの数秒、または保存に失敗したとき）は残る。
   ここが唯一の戻せないデータなので、削除に関わる変更をするときは必ずこの経路を確認する
