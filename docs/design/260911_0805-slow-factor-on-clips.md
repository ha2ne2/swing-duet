## 1. いま起きていること

- 今のコードに倍率は無い。お手本が焼き込みスロー（YouTube のスロー動画、他アプリの書き出し）だと、**お手本基準**の x0.3 は
  「お手本の動画秒の 0.3 倍」＝ 実速の 0.3/N 倍になり、自分の動画もそれに合わせて引き伸ばされるので全体が異様に遅い
- **自分基準**にすると自分（写真ライブラリの原本＝実速）が時間の物差しになり、お手本は区間ごとに伸縮されるので、倍率が無くても x0.3 は実速比になる。
  これが今すぐの回避策。ただし既定はお手本基準で、お手本のテンポに合わせて見たい場面も多い
- 自分の動画は 2026-09-11 から写真ライブラリの原本（120 / 240fps・実速）で取り込むので、倍率が要るのは事実上お手本側だけ
- 検出器は 2026-09-10 に速さに依存しない形（手の高さ）になった。スロー動画でもフェーズが割れず、
  ダウンスイング長（動画秒）が信頼できる値として取れる。倍率の推定はその上に乗せられる

## 2. 設計

### 2.1 データ：倍率は動画の性質

- `VideoConfig.slowFactor: Double = 1`（動画秒 ÷ 実秒。1 / 2 / 4 / 8）。旧データは `decodeIfPresent` で 1。
  選択肢と表示（実速 / 1/2 / 1/4 / 1/8）は `SlowFactor` に置く（stash と同じ）
- フェーズと同じく**動画そのものの性質**なので、お手本ならそのお手本を使う全スイングに効く。比較画面で直したら
  `ComparisonContent.onChange(of: model)` がフェーズと一緒に相手クリップへ書く（`pairing` には入れない）
- 「実速と分かっている」印（写真ライブラリのスローモーション原本なら倍率 1 と確定）は持たない。原本のダウンスイングは 0.3 秒前後なので
  推定でも 1 になり、印を持つ利点が無い

### 2.2 推定：ダウンスイング長から、実速寄りに丸める

`SwingDetector.estimateSlowFactor(downswingDuration:)`。採用した候補のトップ〜インパクト（動画秒）を、実速の代表値 0.3 秒と比べる。

| ダウンスイング長（動画秒） | 倍率 | 根拠 |
| --- | --- | --- |
| 0.52 未満 | 1（実速） | 実速の上限 0.45（アマチュア）と 1/2 の下限 0.6（プロ 0.3 × 2）の幾何平均 |
| 0.52〜1.04 | 2 | 同じく 0.9 と 1.2 の幾何平均 |
| 1.04〜2.08 | 4 | 同じく 1.8 と 2.4 の幾何平均 |
| 2.08 以上 | 8 | |

- トップかインパクトが推定（`SwingCandidate.estimated`）なら 1 にする。当てずっぽうの長さで倍率を決めない
- 境目は実速寄りに切る。倍率を大きく間違えると基準側が何倍速にもなり、相手の伸縮も崩れて目立つ。小さく間違える方が害が少ない。
  実装は stash の「代表値との log2 距離で最近傍」のまま、代表値を 0.3 → 0.37（= 0.52 ÷ √2）にするだけで上の境目になる
- 推定を見送る条件は `lowConfidence`（検出失敗・手首の検出率 40% 未満・トップかインパクトが推定）。stash と同じ
- 隣の倍率との入れ替わり（1/4 と 1/8。プロの 1/8 とアマチュアの 1/4 が 1.6〜1.8 秒で重なる）は内容からは決められない
  （[research/260910_0220](../research/260910_0220-slowmo-detection-failure.md) §2.1）。推定は**提案**で、確定はユーザーの選択
- 手元のサンプルでは：yuta_behind（写真アプリのレンダリング版）ダウンスイング 1.20 秒 → 1/4、YouTube Shorts 0.14 秒 → 1（実速）、Golfboy 0.94 秒（推定フェーズ）→ 1

### 2.3 再生：共通タイムラインを実秒に

- `SyncEngine`：共通タイムラインの長さ = 基準側のスイング区間（動画秒）÷ 基準側の `slowFactor`。各フェーズの位置（`commonTime(of:)`）も同じく割る。
  `rateMultiplier` = その側の区間長（動画秒）÷ 共通タイムライン上の区間長（実秒）。基準側は常に `slowFactor` そのもの、
  非基準側は区間長の比に速さが含まれる。**同期に使うのは基準側の倍率だけ**（非基準側の倍率は表示と、基準を切り替えたときに使う）
- **左右両方が焼き込みスローでも同じ式で正しい。** 例：自分 1/4（基準）・お手本 1/8。共通タイムラインは自分の区間 ÷ 4（実秒）、
  お手本の rate = お手本の区間（動画秒）÷ 共通の区間（実秒）= 8 × （お手本の実区間 ÷ 自分の実区間）。お手本の倍率は式に出てこないが、
  区間長の比に自然に含まれる。基準をお手本に切り替えれば今度はお手本の 8 で割り、自分の rate に 4 が含まれる。
  したがって両側とも倍率が正しく入っていることが条件で、どちらか一方が外れていると、その側を基準にしたときだけ速さがずれる
- `referenceFrameDuration`（コマ送り 1 コマ）= 基準側の 1 フレーム ÷ `slowFactor`
- `PlaybackController`：`rate = speed × rateMultiplier` はそのまま。1/8 のお手本を基準に x1 で見ると `rate = 8`
- ドリフト補正の閾値（80ms）は動画秒で比べている。`currentTime` の揺れは実秒でほぼ一定なので、rate 8 では動画秒で 8 倍に見え、
  閾値を常に超えてシークが連鎖する（音声トラックのときと同じ症状）。閾値を `80ms × max(rate, 1)` にして実秒で揃える。stash には無かった点
- 再生速度のプリセット（0.1〜1.0）と表示「x0.30」は変えない。意味が「実速に対する倍率」になるだけ

### 2.4 画面

- **フェーズ調整**：「動画の速さ」のセグメント（実速 / 1/2 / 1/4 / 1/8）を候補の行の下に足す（stash の `slowFactorRow`）。横に「推定 1/4」を出し、
  いまのフェーズから計算した値を見せる（候補を切り替えれば変わる。`lowConfidence` のときは出さない）。セグメントは自動では動かさず、保存でフェーズと一緒に書く
- **ステージのペインのラベル**：倍率が 1 でなければ「お手本 · マキロイ · 1/8」と添える。速さを直す入口はここ →「フェーズ調整」
- ホームの行・お手本の棚には出さない（増やさない）。stash にあった比較画面の案内文（「お手本を 1/8 スローの動画として扱います…」）と
  速度表示の「実速 x0.3」も入れない（説明文を画面に出さない方針）

### 2.5 既存データ

`Library.version: Int`（旧データは 0）を足し、0 → 1 のとき解析済みの全クリップに §2.2 の推定を掛けて保存する。
いま ★ に入っている 2 本のお手本も、次回起動でここに掛かる（推定が外れていればフェーズ調整で直す）。

### 3.1 実機で分かったこと（2026-09-11、実装後）

- ★ の 1 本の相手「マキロイ ドライバー」（YouTube のスーパースロー、30 秒）は**検出が失敗**していた（人物が小さく写り、追跡が別の点に
  固定されて手の高さが動かない。体の大きさ 0.079）。フェーズはユーザーが手で置いていて、ダウンスイングは動画上 4.9 秒。
  §2.2 の「`lowConfidence` なら推定しない」では、こういう動画で永久に推定が出ない
- 倍率は **1/16**（4.9 ÷ 16 ≈ 0.31 秒）。§2.1 の選択肢 1〜8 では足りない
- 直し：推定を**フェーズの純関数**にし（`VideoConfig.estimatedSlowFactor`。解析時に保存しない）、手でフェーズを置けば追従する。
  検出失敗時の仮のフェーズ（`PhaseSet.fallback`）のままなら手掛かりが無いので 1。`slowFactor` はユーザーの選択だけを持ち（nil なら推定）、
  再生は `effectiveSlowFactor`。選択肢を 1/16・1/32 まで広げた（境目 4.2 / 8.3 秒）。版 1 で全クリップに書いた推定値は版 2 で消し、
  ユーザーの選択（推定と違う値）だけ残す
- フェーズ調整画面のセグメントは、選ぶまで推定値を示して「動画の速さ（推定）」と出す。推定と同じ値を選べば推定に従う状態に戻る
- 残る課題：小さく写る人物の追跡（別件。検出器の話）

## 4. 検討して退けた案

| 案 | 退けた理由 |
| --- | --- |
| 自分の実速のダウンスイングとの比で倍率を決める | プロはアマチュアより速いので比が小さく出る。固定の 0.3 秒より良くならない |
| フリッカー・音声・ランプ検出で 1/4 と 1/8 を分ける | 内容からは決められないことを実測済み。製品には入れない（同 research §2.1） |
| コマ複製の数で確定する | 複製で作られた動画の実サンプルが無い。手が出たら情報源の 2 番目として足す |
| 倍率を `pairing`（比較ごと）に持つ | 動画の性質なので比較ごとに違わない。フェーズと同じ扱いが一番簡単 |
| 実速と分かっている印を持つ | 原本のダウンスイングは推定でも 1 になる。印の分だけ複雑になる |

## 5. 決めてほしいこと

1. 境目（0.52 / 1.04 / 2.08 秒）と実速寄りの丸め。推奨はこのまま
2. 倍率の表示場所。推奨はペインのラベルに「· 1/8」（1 のときは出さない）
3. 既存データへの一括推定。推奨は `Library.version` で 1 度だけ掛ける
