# クラブヘッドの位置追跡と軌跡の表示

- 日付：2026-09-12
- 種別：案出し → 設計 → 実動画での検証（試作 CLI）。アプリのコード変更なし（試作は設計書の隣に置く）
- 試作：[260912_1635-club-head-tracking-prototype/main.swift](./260912_1635-club-head-tracking-prototype/main.swift)（macOS の CLI。§4.1 のビルド手順）
- 対象（実装時）：`Services/ClubTracker.swift`（新規）、`Services/SwingAnalyzer.swift`、`Models/VideoConfig.swift`、`Views/Stage/VideoPaneView.swift`
- 前提：正面（face-on）と後方（down-the-line）の両方に対応する。外部依存ゼロ（Vision / Core Image / Accelerate まで）。
  シミュレータでは Vision が動かないので、検証は Mac の CLI と実機で行う
- 参考：Gehrig, Lepetit, Fua「Visual Golf Club Tracking for Enhanced Swing Analysis」（BMVC 2003、[PDF](https://www.commsp.ee.ic.ac.uk/~ng1/pdf/gehrig-et-al-bmvc03.pdf)）。
  動きマスク（前後フレームとの差の AND）→ 平行な縁の対でシャフト → 極座標の多項式（上げ 4 次・下げ 6 次）を RANSAC で当てはめ、外れ値を弾き欠けを埋める。
  同じ流れを実装した学生レポート（[Chugh, UCSD](https://people.cs.uchicago.edu/~rchugh/static/misc/golf/golfReport.pdf)）は 30fps 実速のブレを最大の問題に挙げている。
  公開実装は YOLO でドライバーのヘッドを学習させたもの（[AICaddy](https://github.com/oswinkil-git/AICaddy-A-Golf-Club-Tracer)。6,000 枚）が主流で、本プロジェクトの制約（外部依存ゼロ・学習データ無し）には合わない

## 1. 何を解きたいか

比較画面の動画の上に、クラブヘッドが通った**軌跡**（線）を重ねたい。正面ならスイングプレーンの円弧と切り返しの形、
後方ならシャフトの通り道（インサイドかアウトサイドか）が一目で分かる。副次的に、手首が体の陰に入る区間（後方視点のトップ〜インパクト）でも
クラブは見えているので、フェーズ検出の欠測を埋める材料になる（[TODO.md](../TODO.md) D）。

必要なのは**フレームごとのヘッドの画像上の位置**（正規化座標）と、その信頼度。3D は要らない。

## 2. 案出し

| 案 | 方法 | 長所 | 短所・見送る理由 |
| --- | --- | --- | --- |
| **A 姿勢起点のシャフト線探索（採用：向きの手掛かり）** | Vision の手首を起点に、シャフトを「動いている細い線」として探し、線の先端をヘッドとする | ヘッドの形・色に依らない。両視点で同じ手順。手首・肘・肩が既にあるので腕を除ける | シャフトが背景に溶ける（明るい空・暗い床）と落ちる。30fps 実速のインパクト前後はブレて線にならない |
| **B 黒いヘッドの塊を運動モデルで追う（採用：位置の本命）** | 動いていて背景より暗い小さな塊を連結成分で取り、前フレームの位置と速度からの予測に最も近いものを追う（滑らかな弧をなぞる前提） | ドライバーの黒いヘッドはどの背景（芝・空・マット）より暗い。ブレても塊は残る。ヘッドの位置が直接出る | ヘッドが暗い背景（夜空）に重なると見えない。アイアン（銀）には効かない。影・バッグなど動く暗い物に貼り付く。開始にはシャフトの線が要る |
| C Vision の物体追跡（`VNTrackObjectRequest`） | アドレスでヘッドの矩形を与えて追跡 | 実装が短い | 速い区間で見失う。初期矩形を決める手段が別に要る。再捕捉できない |
| D オプティカルフロー（`VNGenerateOpticalFlowRequest`） | 画素ごとの流れの大きさが最大の領域 | 速い物が強く出る | 重い（フレームごとに全画素）。三脚前提。ブレると流れも壊れる |
| E ボール検出 + 運動モデル | ボール（小さい明るい円）でアドレスとインパクトのヘッド位置を決め、間は手首からの距離の制約で推定 | アドレスとインパクトは確実 | 途中の軌跡は推定でしかない。練習場のマットではボールが見えないことがある |
| **F 学習した検出器（Core ML）** | クラブヘッドの検出器を学習し、`.mlmodel` を同梱して Vision の `VNCoreMLRequest` で動かす | 精度が最も期待できる。実行時は Apple の Core ML / Vision だけで動き、モデルは同梱するデータなので「外部依存ゼロ」に反しない。学習は Create ML（Mac 標準）で済む | 学習データが要る → **公開データセットがある**（§7）。夜・室内など自分の条件は自分の動画で足す |
| G ゼロショット検出器（YOLO-World 等） | 文章でクラスを指定できる検出器を Core ML に変換して載せる | 学習なし。「golf club」の箱は晴天の後方動画で 65% のフレームに出た（§7） | ライセンスが AGPL（Ultralytics）で配布するアプリには不向き。夜の動画は 9%。ヘッド単体は弱く「クラブの箱の手首から遠い角」で代用する |

2026-09-12 の再考（§7）：**F（学習した検出器）を位置の本命に据え直す**。A・B は検出器の候補が無いフレームの代わりと、候補の検証（線の先端・黒い塊との一致）に回す。
E（ボール）は検出器のクラスに含める。極座標の多項式（§4.3 の 9）は検出器の候補を束ねる後処理として完成させる。

## 3. 設計

### 3.1 パイプライン（解析時に 1 回）

取り込み時の解析（`SwingAnalyzer.analyze`：`PoseTracker` → `SwingDetector`）の後段に **`ClubTracker`** を足す。
フェーズ（アドレス〜フィニッシュ）が決まってから、その前後 0.3 秒だけを対象にする。

1. **フレームの読み出し**：`AVAssetReader` で輝度面（Y）だけを取り、表示向きに回して長辺 640 画素に縮小する。
   解析レートは 30fps（姿勢と同じ）。240fps 原本では 60fps まで上げる価値がある（§5）
2. **背景と動きマスク**：対象区間から等間隔に 40 枚取り、画素ごとの**中央値**（背景）と**中央絶対偏差**（その画素のノイズ）を持つ。
   「前のフレームとも次のフレームとも `max(10, 3.5 × 偏差 + 4)` 以上違う」画素（いま動いている物だけが残る。Gehrig ら）に、
   背景から `max(16, 5 × 偏差 + 6)` 以上離れた画素（トップで止まっているヘッド）を足し、2 画素膨らませる。
   夜の自動露出の揺れは、背景との差の画面全体の中央値を引いて補正する（これを入れる前は鉄骨まで「動いている」になった）
3. **腕の除外**：Vision の手首 → 肘 → 肩の線分から 0.16 体分以内をマスクから外す（手首から 0.35 体分以内は残す。シャフトの根元）。
   後方視点のダウンスイングではシャフトが左腕とほぼ平行（実測 18°）になるので、**方向で腕を除いてはいけない**（§4.3）
4. **リッジ（細い線）の検出**：ガウス平滑化（σ = 1.6）した画像のヘッセ行列の固有値から、画素ごとに「線らしさ」（|λ1| − |λ2|）と線の向きを出す。
   線らしさは局所（半径 10 画素）の標準偏差で割って正規化する。空に映る薄いシャフトは拾い、芝の模様は落とすため
5. **シャフトの投票**：動いていて線らしさ ≥ 0.5 の画素のうち、その画素の線の向きに延ばした直線が手首から 8 画素以内を通るものだけを、
   線の向き（2° 刻み）と手首から見た側で集計する。向きごとに手首側から距離順に並べ、8 画素以上途切れずに続く範囲を「線」とし、
   長さ 0.4 体分以上・密度 50% 以上のものを候補にする。手首から 0.2〜3.0 体分の範囲（ドライバーは腰〜首の約 2.5 倍）
6. **選択**：候補の重み（線らしさの和）に、前フレームのヘッドからの飛び（2 体分で 0.15 倍）と向きの変化（180° で 0.3 倍）の割引を掛け、最大を採る。
   初回は「下向き」を前フレームの向きとみなす（アドレスでは必ずヘッドが手より下にある）
7. **黒い塊の検出**：動いていて（2 のマスク）輝度 90 未満、かつその場所の背景より 25 以上暗い画素の連結成分のうち、面積 (0.05〜0.5 体分)²・最大辺 0.6 体分以下のもの。手首から 3.2 体分の範囲だけ見る
8. **塊の追跡**：前フレームの位置 + 速度で予測し、予測から `max(0.5 体分, 2.5 × 速さ)` 以内で最も近い塊を採る（速度は 0.7 : 0.3 で更新）。
   外れたら見失いとして速度を 0.8 倍ずつ減衰し、6 フレーム続けば追跡をやめる。予測が画面の外なら乗り移らず予測で追い続ける（最大 15 フレーム。トップでヘッドが画面外に出る後方視点用）。
   始めるのは、5 の線の先端から 0.4 体分以内に塊があるとき、またはスイングの始まり（アドレス + 0.8 秒まで）に手首より下・体の外で 3 フレーム続けて現れて動いた塊があるとき（テークバックのヘッド）。
   塊が止まったまま手首だけ動く、またはインパクト後に塊が止まる状態が 6 フレーム続いたら、影やバッグへの貼り付きとして切る（トップの静止は許す）
9. **後処理**：前後 0.25 秒の検出点のどちらからも 1 体分以上離れた点を捨て、0.3 秒以内の欠けを線形補間する。塊の位置を優先し、無い区間は線の先端で埋める。信頼度は塊 > 線 > 補間の順に付ける

### 3.2 データ

```swift
/// クラブヘッドの軌跡（解析レートのフレームごと。スイング区間の前後 0.3 秒）
struct ClubPoint: Codable, Equatable {
    var time: Double
    /// 正規化座標（左下原点。Vision と同じ）。見つからなければ nil
    var head: CGPoint?
    /// 0〜1。補間した点は 0.3 以下
    var confidence: Double
}
```

`VideoConfig.clubPath: [ClubPoint]`（無ければ空。旧データはキー無しで読める）。30fps × 3 秒で 100 点、1/8 スロー原本でも 250 点程度なので JSON のまま持てる。
フェーズを手で直しても軌跡は変わらない（動画に対する事実）。動画の速さの選び直しにも依存しない。

### 3.3 表示

- `VideoPaneView` の映像の上に `Canvas` で折れ線を描く。座標は正規化 → ペインの自動フィットと拡大・位置合わせ（`Transform`）を通すので、
  ピンチしても映像に付いてくる
- 描くのは**現在時刻までの軌跡**（尾を引く形。現在のヘッドに丸）。比較中は 2 本それぞれに描く。色は側ごと（自分・お手本）
- 時刻の対応：`SyncEngine.videoTime(at:for:)` で共通時刻をその動画の時刻にしてから、`clubPath` の `time ≤ 動画時刻` の点を使う
- 信頼度の低い点（補間）は細く・薄く。検出できない区間は線を途切れさせる（無いものを描かない）
- 表示の切り替えはペイン下端の「フェーズ調整」の隣に「軌跡」ボタン。設定は `PlaybackSettings` に持ち、開き直しても続く

### 3.4 正面と後方の違い

手順は同じで、違いは失敗の仕方だけ：

| 場面 | 正面 | 後方 |
| --- | --- | --- |
| アドレス・インパクト | シャフトが脚の前を横切る（脚は太いのでリッジには出ない。静止しているのでマスクで消える） | ヘッドはボールの脇。問題なし |
| テークバック | 問題なし | シャフトがカメラ方向へ縮む（0.3 体分以下）。検出できず、後処理の補間に頼る |
| トップ | シャフトが頭の上で横になる。空に溶けやすい | ヘッドが画面の外へ出ることが多い（画面端で止めて信頼度を下げる） |
| ダウンスイング | 30fps 実速ではブレて扇になる（線にならない） | 左腕と平行に見える（腕を方向で除くと消える） |

## 4. 実動画での検証

### 4.1 手順

```bash
# アプリの解析コードと一緒にビルドする（analyze-swing と同じ）
swiftc -O -o build/clubtrack SwingDuet/Services/{SwingAnalyzer,PoseTracker,SwingDetector}.swift SwingDuet/Models/*.swift \
  docs/design/260912_1635-club-head-tracking-prototype/main.swift

build/clubtrack docs/data/macroy_behind.mp4 build/clubtrack-out/det --model docs/data/datasets/club-detector-v1.mlmodel   # 検出器（§7）の箱を候補に足す
```

`--min`（線らしさの閾値、既定 0.5）、`--rate`（解析レート、既定 30）で振れる。`--model` は Create ML で学習した検出器（§7.2）で、
ヘッドの箱の中心を候補の先頭に置き、CSV の `detX,detY,detConf` と重ね描き（青）に出す。出力画像は人物が写るので `docs/` には置かない。

| --- | --- | --- | --- | --- | --- |
| macroy_behind（1/2 スロー、720p、晴天、黒いドライバー） | 後方 | 27%（57/214） | 29% | **62%（132/214）** | 塊の追跡が、アドレスのヘッド（ボールの脇）からテークバック、トップの弧、滑らかな折り返し、ダウンスイング〜フォローの大きなループを 1 本でなぞる。トップの静止も保つ。フォロー後半で影に貼り付いたが、インパクト後の静止で切れてフィニッシュのヘッドを拾い直す |

**閾値の経緯**（同じ 2 本での検出率）：放射状の線探索だけ → 意味のある線が取れない。中央値背景マスク + 密度 + 連続性 → 53% / 52% だが半分以上が体の線。
リッジ（ヘッセ行列）+ 手首を通る線の投票 + 腕の帯の除外 → 31% / 46%。マスクをノイズ適応に → 27% / 32%（誤検出は減り、薄い線も減る）。

処理時間は Mac で 1 フレーム 25〜60ms（360×640。姿勢推定を除く）。スイング区間 250 フレームで 10〜15 秒。

### 4.3 分かったこと

1. **シャフトは「手首を通る、動いている、細い線」として探せる**。線らしさを局所ノイズで正規化すると、空に溶けた薄いシャフトと芝の模様を分けられる
2. **腕は方向ではなく領域で除く**。後方視点のダウンスイングではシャフトが左腕と 18° しか違わない（試作の途中でこれを方向で除いてしまい、正しいフレームを全部落とした）
3. **動かない線を消すマスクが要**。ネット・地平線・的の線は手首の高さを横切る瞬間に必ず拾われる。中央値背景で大半は消えるが、
   夜の動画のノイズと手持ちの揺れが残る。次は「同じ位置に連続フレームで出る線」を時間方向でも除く
4. **30fps 実速の正面はこの方式では足りない**。インパクト前後 3〜4 フレームは扇状のブレになり線ではない。アプリの主な入力は 240fps 原本
   （[SPEC.md](../SPEC.md) §2）なので、そこではブレは 1/8 になる。次の検証は端末の 240fps 原本で行う（今回は端末が外れていて未）
5. **後方視点ではトップ付近でヘッドが画面の外に出る**。画面端で止めた点は信頼度を下げ、線を途切れさせる
6. 手首の中点はシャフト軸から数画素ずれるので、「線を延長して手首から 8 画素以内」の許容が要る。放射状に手首から探すと外れる
7. **黒いヘッドは塊として追える**。予測（位置 + 速度）に最も近い塊を採るだけで、晴天の後方動画ではスイングの弧が 1 本につながった（66%）。
   トップの静止は許し、インパクト後の静止は切る、という区別で影・バッグへの貼り付きを断てる。弱点は「黒い物が暗い背景に重なる」ことと、銀のアイアン。
   線（A）は塊の追跡を始める合図と、塊が見えない区間の代わりとして残す
8. **夜の練習場で効いたのは露出補正**。自動露出の揺れで背景との差が画面全体で膨らみ、鉄骨やネットの上端が「動いている暗い塊」になっていた。
   画面全体の差の中央値を引くだけで消える。残るのは「黒いヘッドが夜空に重なる」区間で、これは見えないものは見えない（線の向き × 学習したシャフト長で置く推定で少し埋まる）
9. **極座標の多項式モデル（Gehrig ら）は実装したが未完成**。中心を手首の平均に置くと手首がその近くを通って角度が飛ぶので、中心はヘッドの候補の平均に置き、
   角度は前フレームの候補に続く枝で外す必要があった。それでもインライアが 15〜26 本と少なく、欠けを大きな円弧で埋めてしまう。
   論文は「毎フレームに候補が多数ある」前提で、角度の時間変化 β(t) の多項式も併用している。候補の質を上げてからでないと効かない
10. **学習したシャフト長で塊を絞るのは逆効果**（0.35〜1.3 倍で 66% → 43%）。後方視点ではトップ付近で投影が大きく縮む。試作には残していない

### 4.4 使える水準か

黒いドライバー・後方視点・明るい背景なら、塊の追跡でテークバック後半からフィニッシュまでの弧が 1 本で出る。
夜の練習場は塊がトップとインパクトだけ、正面の実速 30fps と暗い室内は線も塊も出ない。
**製品として「軌跡」を出すには、240fps 原本での検証と §5 の対策が先**だが、塊 + 線の組み合わせは実装に進める形になった。

## 5. 残る課題と次の手

| 課題 | 手 |
| --- | --- |
| 動かない線の誤検出（ネット・地平線） | 連続 3 フレームで同じ位置・向きに出る線を「静止線」として除く。カメラの揺れは背景差分の前に小さな並進を推定して合わせる |
| アドレスの初期位置 | ボール（小さい明るい円。`VNDetectContoursRequest` か明度の極大）を探し、アドレスのヘッド位置とシャフトの初期向きに使う（案 E） |
| 240fps 原本 | 解析レートを 60fps に上げ（`--rate 60`）、端末の原本で検出率を測る。ブレが減る分、閾値を上げられるはず |
| ヘッドの端の確定 | 線の先端の先に「動いている塊」（案 B）があればそこまで伸ばす。ドライバーのヘッドは 0.15 体分ある |
| 画面外 | 画面端で止めた点は信頼度 0.2、表示では線を切る |
| 実機の処理時間 | 取り込み時の解析キューで背景実行（既存）。Mac の 10〜15 秒が実機で 30 秒を超えるなら解像度を 480 に落とす |
| 塊が見えない区間（夜空・画面外） | ヘッドの軌道は滑らかな弧なので、見えている区間に極座標の多項式（Gehrig ら。実装済みだが未完成、§4.3 の 9）を当てはめ、欠けを曲線に沿って補外する。角度の時間変化 β(t) も多項式で持ち、候補は 1 フレーム 2〜3 個に絞る。補外は点線で描く |
| 夜の練習場 | 黒いヘッドは夜空では見えないので、そこでは線（照明で明るく見えるシャフト）の向きと学習したシャフト長から置く推定を本命にする。ネットの上端は「連続 3 フレームで同じ位置・向き」の線として除く |
| アイアン（銀のヘッド） | 塊は「暗い」ではなく「背景と違う」（背景差分の大きい小さな塊）で取る。線（A）の先端との一致で選ぶ |
| 正面の実速 30fps | インパクト前後は塊もブレて伸びる。伸びた塊の重心でよしとするか、240fps 原本に限るかを決める |
| 手直し | 自動が外れたときに、ヘッドを指で置く UI（フェーズ調整と同じシート）。第 2 段 |

## 7. 学習モデルの道（2026-09-12 の再考）

世の中の方式（製品・研究）の調査は [research/260913_1124](../research/260913_1124-club-head-tracking-survey.md)。
主流は「クラブを姿勢推定のキーポイントとして体と一緒に学習する」方式で、公開データより自前条件のラベルが効く、という結論。

「外部依存ゼロ」を「学習モデルも使わない」と読み替えていたのが固定観念だった。Core ML のモデルはアプリに同梱する**データ**で、
実行時は Apple の Core ML / Vision だけで動く。学習も Create ML（Xcode 付属。Swift の `MLObjectDetector` からも呼べる）で済み、SPM も CocoaPods も増えない。
[AGENTS.md](../../AGENTS.md) §4.2 の文言は「SPM / CocoaPods を増やさない。同梱する Core ML モデルはこの限りではない」と明確にする（ユーザーの合意が要る）。

### 7.2 手元で試したこと

- **YOLO-World（中型、クラス「golf club」「golf club head」「golf ball」）を全フレームに掛けた**：マキロイ後方 65%（214 本中 140 本。トップの 1/8 区間だけ 1/27 と落ちる）、
  yuta 夜 9%（252 本中 23 本）。箱は正しくクラブ全体を囲み、手首から最も遠い角がヘッドになる。ボールはほぼ全フレームで出る。
  夜は学習データに無い条件なので落ちる。自分の条件の動画でラベルを足せば上がる、という見立て
- **Vision の「前景の被写体マスク − 人物マスク」**（iOS 17、学習なし）：クラブは前景マスクに入らず、残るのは人物の輪郭の縁だけ。使えない
- Create ML の `MLObjectDetector` はこの Mac（macOS 26.5、Xcode の Create ML.app）で Swift から使える
- **Roboflow「Golf club」を取得して中身を確認した**（2026-09-12。置き場所は `docs/data/datasets/`、gitignore）：train 15,972 枚 / valid 2,952 枚、
  すべて 640×640 に引き伸ばし。train は元画像 5,454 枚を「40% までの切り出し・±45° 回転・明るさ ±25%」で 3 倍に水増ししたもの。
  ラベルは 2 クラスで `0` = クラブ全体、`1` = ヘッド（目視で確認。学習用に `club` / `club_head` へ改名）。画角は正面・後方・斜めが混在し、夜の画像はほぼ無い
- **YOLOv8n をこのデータで 1 エポック微調整して 4 本に掛けた**（開発機だけの実験。AGPL なのでアプリには入れない。valid で適合率 0.54 / 再現率 0.41 / mAP50 0.42）：
  枠が出るフレームは 73〜84% と多いが、位置を塊の追跡（§4.2。マキロイでは目視で正しい）と突き合わせると、
  マキロイ後方は一致 45%（信頼度の高い枠ほどグリップ側の端を「ヘッド」と呼んでいて外れる）、yuta 夜は一致 0%（信頼度の中央値 0.20 でほぼノイズ）。
  手首から遠い候補を選ぶ絞り込みを足すとマキロイは 67〜69% まで上がるが、yuta は 0% のまま。
  **公開データだけでは夜・自分の条件に効かない**ので、§7.3 の 2（自分の動画のラベル）が必須。学習は 1 エポック 12 分（M4、16 GB）で、2 エポック目にメモリ不足で止まった
- **Create ML（転移学習 `.transferLearning(.objectPrint())`）の学習パイプラインは通る**：200 枚・40 反復で 34 秒、`.mlmodel` 6.5 MB、入力は 299 px 四方の画像、
  出力は箱と信頼度（NMS 込み、既定の信頼度閾値 0.4、iOS 14+）。ヘッドは 1080p で 20〜40 px と小さいので、姿勢の体の枠を広げた領域を切り出して掛ける（`clubtrack --model`）。
  同期 API は進捗を出さず、一晩走らせた学習が Mac の再起動で消えたので、学習コマンドはジョブ版（`MLObjectDetector.train`。進捗・残り時間・途中保存）にした
- **Create ML で全データを 2,000 反復学習した**（2026-09-13。12 分、`docs/data/datasets/club-detector-v1.mlmodel` 6.8 MB。反復を省略すると `5000 × √枠数 ÷ 32` ≈ 26,000 反復で一晩になる）：
  検証 mAP50 0.30（club 0.44 / club_head 0.16。学習データでは 0.53）。4 本に掛けると、マキロイ後方は 48% のフレームでヘッドが出て、
  塊の追跡と 51/64・線と 27/30 が一致（画面の 0.05 以内）。yuta 夜 0%、Shorts 3/38、Golfboy 1/64。
  昼の後方では「出れば正しい」候補になるが、夜・低解像度・実速には公開データだけでは効かない（YOLO の実験と同じ結論）。
  Create ML の検出器は `VNCoreMLRequest.imageCropAndScaleOption` を **`.scaleFill`** にしないと箱の座標がずれる
  （既定の centerCrop では縦長動画で y が 0.56 倍に縮む。試作の `Detector` に反映済み）

### 7.3 進め方

1. ~~Roboflow の無料アカウントを作り、「Golf club」を Create ML 形式で落とす~~（済。CC BY 4.0 の表示はアプリの About に書く）。残りの 3 データセットは必要になったら足す
2. 自分の動画から 200〜400 コマを切り出し、検出器の箱と塊の追跡を**下書き**にして手で直す（ラベルは club_head と ball。ヘッドの箱はシャフトの先端 0.15 体分四方）。
   素材は用意済み：`docs/data/ownframes/`（4 本のスイング区間の全フレーム 638 枚）と、今日の長回し 2 本（昼・正面 / 夜・後方）をスイングごとに切り出した
   `docs/data/swings/`（32 本。`INDEX.txt` が対応表。`tools/splitswings.py` で動きの山から区間を出し、`tools/cutclip.swift` で再エンコードなしに切る）。夜・後方が重点
3. Create ML（転移学習）で学習（公開データだけの学習は済。結果は §7.2）。学習コマンドは `docs/design/260912_1635-club-head-tracking-prototype/train-detector/`（Swift）、評価は `build/clubtrack --model`
   （4 本の動画のフレーム検出率と、§4.2 の塊・線との一致）。YOLO の実験は同 `tools/detect_video.py`（開発機だけ）
4. 30fps で 214 フレーム × 検出器の推論時間を実機で測る（Neural Engine で 1 フレーム 10〜30ms の見込み）。解析キューで背景実行なので待てる
5. 検出器の候補を §3.1 の 5〜9 に流し込む：候補が出たフレームはそれを採り、無いフレームは線・塊・極座標の補間で埋める
6. 精度が足りなければ RF-DETR / D-FINE（Apache 2.0）で同じデータを学習し、Core ML に書き出して差し替える
