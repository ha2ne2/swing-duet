# iPhone スロー動画（レンダリング版）で x1 が実速にならない原因の調査

**作成日時**: 2026-09-10 02:20 JST
**対象**: コミット `cddaa27` ＋ 未コミットの「動画の速さ（`slowFactor`）」一式
**対象動画**: `docs/data/yuta_behind.MOV`（iPhone 15 のスロー撮影を写真アプリから書き出したもの。gitignore 済み）
**目的**: 取り込んだスロー動画の倍率を推定して再生速度の x1 を実速にする機能が、この動画で効かない理由を突き止め、設計を見直す
**種別**: 調査（コードは変更していない。実験は `docs/data/` の動画と使い捨てスクリプトで行った）

---

## 1. 結論

- 倍率推定そのものではなく、**その手前のフェーズ検出が外れている**のが直接の原因。
  トップでの一瞬の間（実時間 0.2〜0.35 秒）がスローで **1.4 秒**に伸び、検出器の「切り返しの休止は 0.6 秒未満」という
  **動画秒で書かれた閾値**を超えてスイングが 2 つの動作区間に割れる。バックスイングだけの区間からは候補が作れず、
  残った区間では**トップの静止をアドレス**と誤認する（§3）。撮影方向（後方視点）の問題ではなく、時間の伸びの問題
- 誤ったフェーズではトップ〜インパクトに 0.93 秒の欠測がかかって `lowConfidence` になり、
  `SwingAnalysisResult.slowFactor` は推定せず 1（実速）を返す。だから x1 は動画をそのまま流す速さになり、案内文も出ない
- 追跡結果の時間軸を 1/8 に縮めて（＝閾値を 8 倍して）検出し直すと、アドレス・トップは正しく取れる（§4）。
  つまり**検出は動画の速さに依存してはいけない**。速さは検出の前には分からないので、閾値を速さで割る設計は循環する
- 動画自体には倍率の情報が無い（§2）。照明フリッカー・スイングのテンポ・音声まで調べても **1/4 か 1/8 かは決められなかった**（§2.1）。
  内容からの推定は提案どまりにし、確実な情報源（元ファイル、ユーザーの選択）を優先する設計にする（§6）

## 2. 動画の正体

`AVAsset` のメタデータ・全フレームの時刻・隣接フレームの画素差分・フレームごとの平均輝度・音声スペクトルを調べた。

| 項目 | 値 |
| ---- | -- |
| 端末 / OS | iPhone 15 / iOS 26.6.1（`com.apple.quicktime.model` / `.software`） |
| 映像 | 1080×1920（縦）、**30fps 固定間隔**（1014 フレーム、全て 1/30 秒刻み）、33.67 秒 |
| メタデータ | make / model / software / creationdate / `full-frame-rate-playback-intent = 0` のみ。タイムドメタデータトラックは `segment-identifier` だけ |
| トラックのセグメント | 1 つ（時間写像なし） |
| 速さのプロファイル（画素差分） | 0〜1.0 秒: 等速＋ランプ。約 1.1〜31 秒: スロー。32.4 秒〜: 等速（人物が歩き去る） |
| 音声 | スロー区間でもスペクトルは等速区間と同じ（ピッチが下がらない）。倍率の手がかりにならない |

[research/260906_1723](./260906_1723-slow-motion-speed-detection.md) §3.3 の「(B) 写真アプリのレンダリング版」そのもので、
**倍率を示す情報は無い**。スイング（動画 7.7〜16.5 秒）は丸ごとスロー区間に入っているので、スイングの範囲では単一の倍率でよい。

### 2.1 倍率は内容から決められるか（1/4 か 1/8 か）

**照明フリッカー**: 室内照明は電源周波数の 2 倍（東日本 100Hz）で明滅する。背景（画面上半分）の平均輝度を区間ごとに FFT すると、
スロー区間に動画秒 **12.5Hz** の強いピークがある（アドレス 2.0〜6.0 秒: 12.66Hz にエネルギーの 51%。自己相関はラグ 12 = 5 周期で 0.85）。
レンダリング版のスロー区間は原本 1 コマ = 出力 1 フレームなので、これは原本で 2.4 フレーム周期の明滅。

| 撮影 fps | 明滅 100Hz（東日本の一般照明） | 明滅 50Hz（半波整流の LED など） |
| -------- | ------------------------------ | -------------------------------- |
| 240fps | 2.4 フレーム周期 → **12.5Hz** | 4.8 フレーム周期 → 6.25Hz |
| 120fps | 6 フレーム周期 → 5Hz | 2.4 フレーム周期 → **12.5Hz** |

照明が 100Hz なら 240fps（1/8）、50Hz なら 120fps（1/4）。照明の種類が分からないので決まらない。

**スイングのテンポ**: 目視で取ったフェーズ（§2.2）を実秒に直すと、1/8 ではバックスイング 0.48 秒・フォロー 0.19 秒と極端に速く、
1/4 では 0.95 秒・0.38 秒と一般的。テンポは 1/4 を支持するが、本人が速いテンポなら 1/8 でも成り立つ。

**結論**: Mac 上で全フレームを解析しても 1/4 と 1/8 は決められない。決め手は写真アプリの動画情報（120 / 240 FPS の表示）だけ。
アプリ内で内容から推定する仕組みは、どれだけ作り込んでも**提案以上にはならない**。

### 2.2 本当のフェーズ（映像を目視）

| フェーズ | 動画秒 | 実秒（1/4 なら） | 実秒（1/8 なら） |
| -------- | ------ | ---------------- | ---------------- |
| アドレス（静止） | 〜7.7 | — | — |
| バックスイング | 7.7〜11.5 | 0.95 秒 | 0.48 秒 |

## 3. 何が起きているか

`build/analyze-swing docs/data/yuta_behind.MOV` の出力：

```
検出率=88%
注意: 採用スイングの切り返し〜インパクトがブレで未観測（信頼度低）
動画の速さ: 実速（ダウンスイング 1.60 秒。信頼度低のため推定せず）
★ 候補1: A=12.83 T=14.67 I=16.27 F=17.13 (テンポ 1.1 : 1)  gap=0.93s
```

検出したフェーズを本当の動きに重ねると、**1 つずつ後ろにずれている**：

| 検出 | 実際 |
| ---- | ---- |
| アドレス 12.83 | トップの間（手首が 1.4 秒静止） |
| トップ 14.67 | インパクト（「アドレス」から最も離れた点） |
| インパクト 16.27 | フィニッシュ（手首が「アドレス」= トップ位置の近くへ戻った点） |
| フィニッシュ 17.13 | フィニッシュの保持 |

経路：

1. `motionSegments`（速度が最大の 20% 以上の区間をつなぐ。低速の連なりが **0.6 秒**以上なら分割）で、
   バックスイング（9.0〜10.8 秒）とダウンスイング以降（13.1 秒〜）の間の 2.2 秒が休止と判定されて 2 区間に割れる
2. バックスイングだけの区間は「アドレス位置へ半分以上戻る」点が無いので `swingCandidate` が nil
3. ダウンスイング以降の区間では、区間の手前で 0.15 秒静止している点 = トップの間がアドレスになる
4. この「ダウンスイング」（実際はフォロー）で手首を 0.93 秒見失っている（インパクト直後〜フィニッシュ手前で Vision の手首が止まる。
   画素差分では動きがあるので追跡側の問題。[TODO.md](../TODO.md) D と同根）→ `downswingUnobserved` → `lowConfidence`
5. `SwingAnalysisResult.slowFactor` は `lowConfidence` なら推定しない → `VideoConfig.slowFactor = 1`
6. 比較画面では `slowFactor == 1` なので案内文も出ず、ユーザーには「x1 でも遅い」とだけ見える

なお `lowConfidence` でなかったとしても、誤ったダウンスイング長 1.60 秒からの推定は 1/4（境目 1.7 秒のすぐ下）になる。

## 4. 閾値を速さで割ると通るか（実験）

追跡結果 `PoseTrack` の時刻を 1/N にしてから `SwingDetector.detect` を呼ぶ（検出器の秒閾値を N 倍するのと等価。コードは変更していない）。

| 時間軸 | 検出（動画秒に戻した値） | 欠測 | 推定倍率 |
| ------ | ------------------------ | ---- | -------- |
| 1/1 | A=12.83 T=14.67 I=16.27 F=17.13 | 0.93 秒 | （推定せず） |
| 1/2 | A=12.73 T=14.67 I=16.27 F=17.03 | 0.93 秒 | （推定せず） |
| 1/4 | A=12.53 T=14.67 I=16.27 F=20.50 | 0.90 秒 | （推定せず） |
| **1/8** | **A=7.90 T=12.10 I=15.27 F=21.30** | 0.03 秒 | 1/8（ダウン 3.17 秒） |

- 1/8 でアドレス・トップが本当の位置（7.7 / 11.5〜12.9）に乗る
- 1/4 でも割れたまま。トップの休止 2.2 秒が閾値 0.6×4 = 2.4 秒のすぐ下で、ぎりぎり
- 1/8 でもインパクトは 0.5 秒（動画秒）遅い。手首がインパクト直後に (0.42, 0.43) で止まって見える追跡の癖のため。
  フィニッシュも 5 秒遅い（静止 0.2×8 = 1.6 秒が要るが、フィニッシュ保持中に人物が動く）

同じ実験を実速の 2 本にかけると、時間軸を縮めるほど候補が崩れる（YouTube Shorts は 1/2 で 2 つのスイングが 1 候補に合体し、倍率 1/4 と誤推定）。
**複数スケールで検出して良い方を選ぶ**方式は、選択基準を設計しないと実速動画を壊す。

## 5. 倍率推定の限界

- 選択肢は 2 倍刻み（1 / 2 / 4 / 8）。境目は代表値 0.3 秒の ±√2 倍（0.42 / 0.85 / 1.7 秒）
- アマチュアのダウンスイングは実速で 0.2〜0.45 秒と 2.25 倍の幅があり、境目の幅（√2 = 1.41 倍）より広い。
  つまり検出が完璧でも **1/4 と 1/8 は本人のテンポ次第で入れ替わる**。この動画（ダウン 1.8 秒）は境目 1.7 秒のすぐ上で 1/8 と推定され、
  真値が 1/4 なら 1 段外れる
- バックスイング（0.7〜1.2 秒）やスイング全体（1.2〜2.3 秒）で見ても幅は同程度。人物の大きさで正規化した手首速度など複数の手がかりを
  対数平均すれば分散は減るが、それでも境目の幅に対して十分ではなく、しかも検出の構造が正しいことが前提になる
- 動画側の手がかりは §2.1 のフリッカー（室内限定・照明の種類で二義的）とランプの形（写真アプリのレンダリング版限定）だけで、一般解にならない。
  コマ複製で作られたスロー（[TODO.md](../TODO.md) G）だけは複製数がそのまま倍率で、これは正確

## 6. 設計の見直し

### 6.1 原則

1. **検出は動画の速さに依存しない**（scale-free）。トップの間は実時間で 0.4 秒程度までありうるので、1/8 なら動画上 3 秒の休止で
   スイングが割れてはいけない。休止・静止・欠測の閾値を絶対秒で持たず、スイング自身の動きに対する相対値か空間的な構造
   （アドレス位置から離れて戻る 1 往復）で決める。追跡の連続性（欠測）は秒ではなく解析フレーム数で見る。
   これは検出の再設計（別ブランチ）への要件として渡す
2. **速さは再生のパラメータであって、検出の入力ではない**。だから取り込み後いつでも直せてよく、取り込み画面に選択を足す必要はない
3. 速さの情報源は確実なものから順に使う：

   | 優先 | 情報源 | 確実さ | 状況 |
   | ---- | ------ | ------ | ---- |
   | 1 | 元ファイル（PhotoKit `.original`。120 / 240fps・実速） | 確実（倍率 1） | [TODO.md](../TODO.md) A。写真アプリから選ぶ自分の動画はこれで解決 |
   | 2 | コマ複製の数 | 確実 | [TODO.md](../TODO.md) G。他アプリの書き出しに多い |
   | 3 | ユーザーの選択 | 確実 | 写真アプリの表示（120 / 240 FPS）を見れば分かる。AirDrop で届いたレンダリング版・お手本の焼き込みスローはこれ |
   | 4 | ダウンスイング長からの推定 | 提案 | 既定値にする。隣の倍率と入れ替わりうることを UI で隠さない |

   写真アプリのスロー動画で元ファイルが取れないとき（iCloud 未ダウンロードなど）は、`requestAVAsset(.current)` が返す
   `AVComposition` の `timeMapping` が公開 API で速度プロファイルを持つ。必要になったら使う
4. **速さが再生に効くのは基準側だけ**（`SyncEngine` は基準側の `slowFactor` しか使わない。非基準側の速さは区間長の比に含まれる）。
   自分の動画が元ファイル（倍率 1）で基準なら、お手本が焼き込みスローでも x1 は自分の実速になる。
   お手本を基準にしたときだけお手本の速さが要る

### 6.2 現行実装との差分

- 検出器の秒閾値（休止 0.6 / 静止 0.15・0.2 / 欠測 0.25 秒、`downswingUnobserved` の 0.2 秒）を原則 1 に沿って置き換える（別ブランチ）
- 速さの選択は今のフェーズ調整画面の Picker でよいが、比較画面からも 1 タップで届くようにする（側ごとの「実速 / 1/8」チップなど）。
  `lowConfidence` で推定を見送ったときも案内を出す（今は `slowFactor == 1` だと何も出ない）
- フェーズ調整画面でスイング候補を切り替えても `slowFactor` は取り込み時の推定のまま残る。推定はフェーズの純関数なので、
  候補を切り替えたら推定し直して「推定: 1/8」と Picker の横に示し、選択はユーザーの値として別に持つ
- `SyncEngine` / `PlaybackController` は変更不要。`rate = 8` の滑らかさは実機未確認（[ROADMAP.md](../ROADMAP.md) フェーズ 2）

### 6.3 今すぐの回避策

比較画面 → フェーズ調整（自分側）で「動画の速さ」を写真アプリの表示に合わせて **1/8 か 1/4** にし、フェーズも手で直す
（アドレス 7.7 / トップ 12.3 / インパクト 14.7 / フィニッシュ 16.3 秒付近）。保存すれば x1 が実速になる。

## 7. 実験に使ったもの

使い捨てスクリプト（リポジトリには入れていない）：`AVAssetReader` で全フレームの時刻・縮小輝度の差分・平均輝度を出すもの、
音声を PCM で読んで区間ごとのパワースペクトルを対数周波数で相互相関するもの、`PoseTrack` の時刻を 1/N にして `SwingDetector.detect` を呼ぶもの。
フェーズの目視は `AVAssetImageGenerator` で並べたサムネイルで行った。再現が要るなら `scripts/analyze-swing/` に `--scale` を足すのが早い。
