# 後方（ダウン・ザ・ライン）動画でフェーズ検出が外れる原因

**作成日時**: 2026-09-10 02:15 JST
**対象**: `docs/data/` の後方視点サンプル 2 本（gitignore）
- `macroy_behind.mp4` — プロのスロー再生クリップ。29.6fps、720×1280、11.4 秒、手首検出率 100%
- `yuta_behind.MOV` — 練習場で撮った自分の動画。30fps、1080×1920（回転メタデータ付き）、33.7 秒、検出率 88%

**目的**: 「後方からのスイングだと自動フェーズ検出がうまく動かない」の原因を実データで確認し、対策の選択肢を整理する。
検出ロジックの現状は [ARCHITECTURE.md](../ARCHITECTURE.md) §5、閾値の根拠は [260906_1641](./260906_1641-multi-swing-detection.md)。

> **訂正（2026-09-10）**: yuta の動画は iPhone のスロー撮影（1/4〜1/8）で、本稿 §2〜§3 の「リハーサル → アドレスで静止 → 本番」という読みは誤り。
> 写っているのは 1 つのスイングで、「アドレスで静止 14.6〜15.05」はインパクト付近（後方視点では手が奥へ動いて画面上は止まって見える）、
> 「本番 15.07〜」はフォローだった。トップの間が長いのもスローで伸びたため。詳しくは atelier ブランチの research/260910_0220-slowmo-detection-failure.md と
> [design/260910_0236](../design/260910_0236-hand-height-phase-detection.md) の訂正。§3.2 の「手首が体の陰に入る」観察と、
> 「静止をアドレスに取ると 1 つずつずれる」機構の分析は正しい。

---

## 1. 結論

1. **2 本とも直接の原因は「後方」ではなく、スイング前にトップで 2 秒以上静止していること。**
   検出器は「動作区間の手前で静止している点 = アドレス」とみなすため、トップの静止をアドレスに取り、
   以降のフェーズが 1 つずつずれる（トップ→アドレス、インパクト→トップ、フィニッシュ→インパクト）。
   トップの静止を抜いた合成クリップでは、後方視点のままで macroy を正しく検出できた（§3.1）。
2. **後方視点に固有の問題は別にあり、こちらは静止を除いても解けない。** 自分の動画（yuta）では、リード側（左）の手首がスイング中ずっと体に隠れ、
   トレイル側（右）もバックスイング途中から見失う。トップ〜インパクトの 0.8 秒が欠測し、「手首がアドレス位置へ戻る」を一度も観測できないため、
   本番だけを切り出したクリップでも候補が 1 つも作れず、フォールバック値になる（§3.2）。
3. 副次的に、手首の信頼度が閾値 0.3 の境をまたぐと「両手首の中点」と「片方の手首」が切り替わって位置が飛び、偽の速度ピークになる。
   macroy の最大速度（0.79）はこの飛びで、本物のダウンスイングのピーク（0.6）より大きい。相対閾値（最大速度の 20% / 10%）を押し上げる（§3.3）。
4. 対策は 3 段階で考える（§4）。まず「アドレスは手が低い位置にある静止点」という条件を足して 1 の取り違えを止める（小）。
   次に、手首が隠れている間のトップ・インパクトを腰・首の位置と欠測区間から推定する（中、後方視点の本質的な対策）。
   長期的には ROADMAP のクラブヘッド追跡。

## 2. 動画の内容と現在の検出結果

目視（0.07〜0.25 秒刻みのコマ一覧）で読んだ実際のフェーズと、`build/analyze-swing` の結果。

| 動画 | 実際の流れ（秒） | 検出結果 A / T / I / F（秒） | 何が起きたか |
| --- | --- | --- | --- |
| macroy | アドレス 0〜2.0 → バックスイング 2.0〜3.3 → **トップで静止 3.3〜5.6** → インパクト 6.65 → フィニッシュ 8.4〜 | 5.34 / 6.80 / 8.15 / 8.69（テンポ 1.1 : 1） | トップの静止をアドレスに取り、1 つずつずれた。信頼度低にもならない（欠測なし） |
| yuta | アドレス 8.0 → ゆっくりバックスイング 8.3〜10.8 → **トップで静止 11〜13** → ゆっくり下ろす 13〜14.5 → **アドレスで静止 14.6〜15.05** → 本番：テイクバック 15.07、トップ ≈ 15.85、インパクト ≈ 16.18、フィニッシュ 16.6〜 | 12.83 / 14.67 / 16.27 / 17.13（テンポ 1.1 : 1、欠測 0.93 秒） | 同じ取り違え。リハーサル（トップ→アドレス）をバックスイング、本番全体をダウンスイングと解釈 |

後方視点ではトップとフィニッシュの手首位置がほぼ同じ（macroy 0.03、yuta 0.06。正面の YTDown でも 0.10）なので、
「アドレス（実はトップ）からいったん離れて、また戻ってきた」という検出器の条件を、フィニッシュが満たしてしまう。
正面でもこの距離は小さく、取り違えは視点に関係なく起きる。

## 3. 原因の詳細

### 3.1 トップの静止で動作区間が割れ、トップがアドレスになる（両方）

`motionSegments` は速度が最大値の 20% 以上の区間を 1 スイングとし、低速が 0.6 秒（`pauseMax`）以上続くと区間を切る。
macroy では最大速度 0.79 → 動作閾値 0.157、静止閾値 0.079。

| 区間 | 手首の動き | 候補になるか |
| --- | --- | --- |
| 2.0〜3.4 秒（バックスイング） | (0.46, 0.43) → (0.23, 0.66)。アドレス位置から離れるだけで戻らない | ならない（インパクトが見つからず nil） |
| 3.4〜5.6 秒 | 速度 0.03〜0.11 で 2.1 秒静止 → 区間が切れる | — |
| 5.6〜8.4 秒（ダウンスイング〜フィニッシュ） | 手前の静止 5.31〜5.44 秒が「アドレス」に採用（A = 5.44 − 0.1）。そこから最も離れた 6.80 秒（実際のインパクト付近）が「トップ」、戻ってきた 8.15 秒（フィニッシュ）が「インパクト」 | なる（唯一の候補なので score 1.0 で採用） |

**静止を抜くと解ける**: 3.5〜5.5 秒を切り取って前後をつないだクリップでは A=1.56 / T=3.50 / I=4.53 / F=6.69
（元の時刻に戻すと I=6.53、F=8.69）と、目視のインパクト 6.65 秒に対して 0.1 秒差で検出できた。後方視点の幾何自体は、手首が追えていれば現行の「アドレス位置との距離」モデルで問題ない。

yuta も同じ機構：最大速度 0.447 → 動作閾値 0.089。トップの静止（11〜13 秒）で区間が切れ、13.07 秒から始まる区間の手前の静止（12.83 秒）がアドレスになる。
本番直前のアドレスの静止（14.6〜15.05 秒、0.45 秒）は `pauseMax` 0.6 秒より短いので区間が切れず、リハーサルと本番が 1 区間になる。

### 3.2 後方視点では手首が体に隠れ、「戻り」を観測できない（yuta）

本番の手首を左右別に見た（Vision の信頼度。0.3 未満は現行ロジックで「見えていない」扱い）：

| 時刻（秒） | 左手首（リード側） | 右手首（トレイル側） | 腰（root）/ 首（neck） | 状況 |
| --- | --- | --- | --- | --- |
| 14.9〜15.0 | 0.4 → 0 | 0.8 | 0.5 / 0.7 | アドレス。左手首はここで既に消える |
| 15.07〜15.33 | 0 | 0.8 → 0.31 | 0.5 / 0.75 | テイクバック。右手首だけで追えている |
| 15.37〜15.60 | 0 | 0.10〜0.19（位置は妥当） | 0.5 / 0.75 | バックスイング後半。閾値未満で捨てられる |
| 15.63〜16.13 | 0 | 0 | 0.5 / 0.7 | **トップ〜ダウンスイング〜インパクト。両手首とも完全に消える** |
| 16.17〜16.30 | 0.2 → 0.3 | 0 → 0.2 | 0.55 / 0.8 | インパクト直後、体の左側から手が出てくる |
| 16.4〜 | 0.5〜0.7 | 0.3〜0.6 | 0.55 / 0.75 | フォロー〜フィニッシュ |

後方から見ると、バックスイングで両手が体（と頭）の向こう側へ回り込み、インパクト直前まで戻ってこない。
正面（Golfboy）でもトップ〜インパクトはブレで 0.8 秒欠測するが（[TODO.md](../TODO.md) D）、そちらは「ブレ」なので手首がアドレス位置を通過する前後は観測できる。
後方は「遮蔽」なので、**手首がアドレス位置に戻る瞬間そのものが見えない**。

その結果、本番だけ（14.4〜18.0 秒）を切り出したクリップでも `検出失敗 → フォールバック` になる。
アドレス (0.42, 0.43) から離れ始めた手首が次に現れるのはフィニッシュ側 (0.14, 0.63) で、
検出器はこれを「まだトップへ向かっている」と読み、戻りが無いので候補を作らない。
元の動画で候補ができたのは、トップの静止を誤ってアドレスに取った位置とフィニッシュが偶然近かったからで、正しい候補ではない。

一方、腰と首はスイング中ずっと信頼度 0.5〜0.8 で取れている。手首が見えない間の手掛かりとして使える（§4）。

### 3.3 手首の中点が飛んで偽の速度ピークになる（macroy）

`wristPoint` は両手首が見えれば中点、片方なら その手首の位置。後方視点では片方の手首の信頼度が 0.3 前後を上下するため、
1 フレームで「中点 ↔ 片手」が切り替わって位置が 0.05〜0.1 飛ぶ。3 点メディアンは単発の外れ値しか消せず、レベルの切り替わりは残る。

- 7.24〜7.71 秒: 左手首の信頼度 0.13〜0.20 で無視 → 右手首のみ。7.74 秒に左が 0.54 で復帰 → 中点へ 0.085 飛ぶ → 速度 0.5
- 7.95 → 7.98 秒: 右手首の推定が (0.50, 0.61) から (0.30, 0.65) へ 0.2 飛ぶ（フォロー中に古い位置に張り付いていた誤検出） → 速度 0.75〜0.79 = **この動画の最大速度**
- 本物のダウンスイングのピークは 6.05 秒の 0.61

最大速度が 3 割かさ上げされ、動作閾値・静止閾値・採点のピーク速度がその分ずれる。今回の取り違えの主因ではないが、後方視点で常に起きうる。

## 4. 対策の選択肢

> この後の設計レビュー（[design/260910_0236](../design/260910_0236-hand-height-phase-detection.md)）で、距離モデルを残す P1〜P3 は採らず、
> フェーズを「体に対する手の高さ」で決めるモデルへの置き換えを決めて実装した。以下は当時の案として残す。

| 案 | 内容 | 直る問題 | 変更範囲 | 懸念 |
| --- | --- | --- | --- | --- |
| **P1 アドレスは「手が低い」静止点に限る** | `PoseTrack` に腰・首の位置を持たせ、手首の高さを (wrist.y − root.y) / (neck.y − root.y) で正規化。アドレス候補の静止点は高さ ≲ 0.5 に限定し、高い位置の静止（トップ）では区間を切らずつなぐ | §3.1 の取り違え（両方） | `PoseTracker` にジョイント追加、`SwingDetector` のアドレス探索と `motionSegments` | 腰・首の欠測時は現行どおりに退避。スロー動画でも高さは不変なので倍率に依存しない |
| **P2 欠測区間をまたいでトップ・インパクトを推定** | アドレスの後、手首が「低い→（欠測）→高い」と変わったら、トップとインパクトは欠測の中にあるとみなす。インパクト = 再出現の直前（yuta では再出現 16.23 に対し実際 16.18）、トップ = インパクトからテンポの事前値（実速で 0.25〜0.3 秒）だけ前。`lowConfidence` を必ず立てる | §3.2（後方視点で候補が作れない） | `SwingDetector.swingCandidate` | スロー再生動画では事前値が使えない（TODO E と同根）。粗い推定なので手動修正前提 |
| **P3 手首点の連続性** | 片手首だけになったとき中点との差分（直前の左右差ベクトル）を補って飛びを抑える。直前の点から 0.1 以内なら信頼度 0.15 まで採用（ヒステリシス） | §3.3。yuta の 15.37〜15.60 秒も追えるようになる | `PoseTracker.wristPoint` / `medianFiltered` | 誤検出を拾う可能性。閾値は 2 本 + 正面 2 本で確認する |
| P4 高さベースのフェーズモデルへ置き換え | 「アドレス位置との距離」ではなく、体に対する手の高さの低→高→低→高でフェーズを決める | 視点に依存しない形になる | `SwingDetector` の作り直し | P1〜P3 の延長で足りるなら過剰。クラブヘッド追跡（ROADMAP）と役割が重なる |
| P5 テンポの妥当性チェック | ダウンスイングがバックスイングより長い候補（今回は 1.1 : 1）を `lowConfidence` にする | 誤検出を黙って採用しなくなる | `SwingAnalysisResult.lowConfidence` | 直すわけではない。Golfboy の正しい候補（0.8 : 1、欠測の両端）も引っかかる |

**推奨**: P1 + P3 を 1 つの実装タスクとして先に行い（小さく、正面の 2 本に副作用がないことを CLI で確認できる）、
その上で P2 を後方視点向けの 2 段目とする。P4 は P2 で足りないときに検討。P5 は UI で信頼度を使う話が戻ってきたときに。

実装前に決めること：
- 静止が続くトップ（macroy は 2.1 秒）の「トップ時刻」をどこに置くか。静止の終わり（切り返し）に置けば同期のダウンスイング区間が正しくなる
- P2 の事前値をどう持つか（固定秒か、動画のフレームレートやバックスイング長からの比か）

### 運用上の回避策（今すぐ）

- 撮影時はアドレスから始め、リハーサルやトップでの止めを入れない。素振りは今のロジックで分離できるが、「途中で止める」動作は分離できない
- 外れた結果はフェーズ調整画面で直す。後方視点ではトップが手動修正前提になることを、手順としては受け入れる

## 5. 再現手順

```bash
# CLI のビルド（docs/guides/build-test.md）
swiftc -O -o build/analyze-swing SwingDuet/Services/{SwingAnalyzer,PoseTracker,SwingDetector}.swift \
  SwingDuet/Models/{SwingModels,Geometry}.swift scripts/analyze-swing/main.swift
build/analyze-swing --series docs/data/macroy_behind.mp4 docs/data/yuta_behind.MOV
```

調査では次の使い捨てツールを別途書いた（リポジトリ外。必要なら `scripts/analyze-swing/` に取り込む）：

- 指定区間のコマを等間隔に並べたコンタクトシート（`AVAssetImageGenerator` + AppKit）— 目視でフェーズ時刻を読むため
- 手首を左右別に信頼度付きで出す Vision ダンプ — `analyze-swing` は中点しか出せないので、遮蔽の分析に必要だった。`--joints` オプションとして足す価値がある
- `AVMutableComposition` で区間を切り出し・つなぎ直すクリップ生成 — 「静止を抜いたら検出できるか」の対照実験に使った

合成クリップの結果：

| クリップ | 結果 |
| --- | --- |
| macroy から 3.5〜5.5 秒（トップの静止）を抜く | A=1.56 / T=3.50 / I=4.53 / F=6.69 → 正しく検出（元時刻で I=6.53、目視 6.65） |
| yuta の 14.4〜18.0 秒（アドレスの静止 + 本番のみ） | 検出失敗 → フォールバック。手首が戻る瞬間が見えないため |
