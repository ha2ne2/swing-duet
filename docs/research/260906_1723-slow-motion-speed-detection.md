# スロー動画の倍率判別と「x1 = 実速」再生の調査

**作成日時**: 2026-09-06 17:23 JST
**対象**: コミット `ae1e742` ＋ 未コミットの速度プリセット変更（速度表示タップで 0.1 / 0.2 / 0.3 / 0.5 / 1.0 を巡回）
**目的**: 読み込んだ動画が「何倍速のスロー動画か」を判別し、実世界の速さ（実速）で再生できるようにする。
速度表示の x1 を「実速」にしたい、という要望に対して、判別できるか・どうやるか・再生側に何が要るかを整理する。
**種別**: 調査（コードは変更していない）

---

## 1. 結論

- スロー動画は 3 類型に分かれ、**判別できるかどうかは類型で決まる**（§3）

  | 類型 | 例 | 倍率の判別 | 実速で再生するには |
  | ---- | -- | ---------- | ------------------ |
  | (A) 高フレームレート原本 | iPhone スロー撮影の元ファイル（120 / 240fps） | フレームレートから自明。原本は**実速**（倍率 1） | `AVPlayer.rate = 1` のまま。すでに実速 |
  | (B) 写真アプリの「スローモーション」 | 写真アプリが (A) を取り込んだもの | PhotoKit で判別でき、原本も取れる（[TODO.md](../TODO.md) A）。PhotosPicker 経由のレンダリング版は**可変速**（等速 → 約 0.5 秒のランプ → 1/8 → ランプ → 等速。§3.5 で実測）で単一倍率では表せない | 原本 (A) を取得する |
  | (C) 焼き込み済みスロー | Golfboy 等の書き出し、YouTube のスロー動画 | **メタデータは無い**（実測）。スイング所要時間の事前知識からの推定か、手動指定 | 推定した倍率で `rate` を上げる |

- (C) の推定は「ダウンスイングは実速で 0.2〜0.45 秒」という事前知識を使えば、欠測なく検出できている限り **4 倍以上のスローは確実に分かる**が、
  実速と 1/2 の境目は現状の検出精度（30fps 実速のブレ欠測、[TODO.md](../TODO.md) D）では誤る。
  自動値は**提案**に留め、手動で上書きできる UI を必須にする（§3.4）
- 「x1 = 実速」は、動画ごとに倍率（動画上の秒 ÷ 実世界の秒）を持ち、`AVPlayer.rate = 速度 × 倍率 × 区間倍率` にすれば実現できる。
  同期写像とテンポ比は区間長の**比**で決まるので影響を受けない（§4）。8 倍再生が実機で滑らかかは未確認
- **推奨**: (1) 写真アプリ経路は原本取得（TODO A）で倍率 1 に揃える、(2) 焼き込みスロー向けに「倍率」を保存データに追加し、
  取り込み時の推定値＋手動選択で決める、(3) 上記を設計タスクとして起こす（§5）

## 2. 現状の速度モデルと問題

`PlaybackController.speed`（0.1〜1.0）に `SyncEngine.rateMultiplier`（区間ごとの伸縮）を掛けて `AVPlayer.rate` にしている。
コメントは「実時間に対する倍率」だが、実際には**基準側動画のタイムラインに対する倍率**で、x1 = 動画を等速で流す、である。

| 読み込んだ動画 | x1 の実速換算 | x0.1 のとき画面に出るコマ数 |
| -------------- | ------------- | --------------------------- |
| 240fps 原本（実速） | 実速 | 24 コマ/秒（滑らか） |
| 30fps 実速（Golfboy、通常撮影） | 実速 | 3 コマ/秒（カクつく） |
| 30fps に焼き込んだ 1/8 スロー | 実速の 1/8 | 3 コマ/秒（実速の 1/80） |

つまり同じ「x0.3」でも、動画の種類によって見える速さが 8 倍違う。倍率を動画ごとに持てば、
速度表示を実速基準に統一でき、焼き込みスローでも x1 で実速が見られる。

副次的な論点として、`SwingAnalyzer` の閾値（`frameRate / 30` の間引き、欠測 0.25 秒、切り返しの休止 0.6 秒）は動画上の秒で書かれている。
焼き込みスローでは実時間換算で 8 倍細かい閾値になるが、動作区間の分割は最大速度に対する相対閾値なので大きくは崩れない見込み
（焼き込みスローの実サンプルが無く未検証。`docs/data/` の 2 本はどちらも実速）。

## 3. スロー動画の類型と判別材料

### 3.1 実測に使った動画

iPhone 16e シミュレータ（iOS 26.2）の写真ライブラリと `docs/data/` の動画を、調査用スクリプト
（`AVAsset` のメタデータ・トラック情報・全フレームの時刻・隣接フレームの画素差分を出す。リポジトリには入れていない）で調べた。

| 動画 | 出所 | fps | 長さ | メタデータ | 隣接フレームが同一（コマ複製） |
| ---- | ---- | --- | ---- | ---------- | ------------------------------ |
| 合成スイング 240fps | `gen-swing-video.swift` → `simctl addmedia` | 239.9 | 3.00 s | なし | 静止区間のみ |
| 合成スイング 60fps | 同上 | 60.0 | 3.00 s | なし | 静止区間のみ |
| Golfboy 書き出し | `docs/data/Golfboy_FormMovie (16).mp4` | 30.9（間隔 0.0317 / 0.0333 s の混在） | 4.05 s | なし | 0 / 124 |
| YouTube Shorts | `docs/data/YTDown.com_..._720p.mp4` | 30.0 | 6.85 s | `©too = Lavf62.12.100`（エンコーダ名のみ） | 0 / 204 |

実写 2 本にはフレームレート以外に「元の速さ」を示す情報が**無い**。

### 3.2 (A) 高フレームレート原本

- `AVAssetTrack.nominalFrameRate` が 120 / 240 なら iPhone のスロー撮影の元ファイル。時刻軸は実時間で、`rate = 1` が実速
- 240fps の動画を `rate = 1` で再生すると表示は 60Hz に間引かれるが、コマ送りは 1/240 秒単位でできる（[SPEC.md](../SPEC.md) §2.1 の前提）
- 現状のアプリにはこの経路で動画が届かない（PhotosPicker がレンダリング版を渡す。§3.3）

### 3.3 (B) 写真アプリのスローモーション

写真アプリは高フレームレートの動画を取り込むと「スローモーションビデオ」として扱う（PhotosPicker のセルのアクセシビリティラベルもそうなる）。
スロー効果は元ファイルを書き換えず、**編集情報**として別に保持している。シミュレータで実測した内容：

- 編集情報: `Media/PhotoData/Mutations/DCIM/100APPLE/IMG_0007/Adjustments/Adjustments.plist`
  - `adjustmentFormatIdentifier = com.apple.video.slomo`、`adjustmentFormatVersion = 1.1`
  - `adjustmentData`（バイナリ plist）: `slowMotion.rate = 0.125`（1/8）、`slowMotion.regions = [ { start 0.45 s, duration 2.1 s } ]`
- 元ファイル `IMG_0007.MOV` は 240fps・3.00 秒のまま（§3.1）
- PhotosPicker の `FileRepresentation(contentType: .movie)` が渡すのは **30fps・14.67 秒**のレンダリング版
  （[research/260906_1531](./260906_1531-simulator-verification.md) §4.1）。
  等速 0.45 秒 ＋ 1/8 で 2.1 秒 ＋ 等速 0.45 秒を単純に足すと 17.7 秒になるので、
  境界に**ランプ**（徐々に遅く / 速くなる区間）が入っている。実測した速度プロファイルは §3.5

PhotoKit で扱うと、この類型は判別も原本取得もできる：

| API | 得られるもの |
| --- | ------------ |
| `PHAsset.mediaSubtypes.contains(.videoHighFrameRate)` | スローモーション扱いかどうか |
| `PHImageManager.requestAVAsset(forVideo:options:)` + `PHVideoRequestOptions.version = .original` | 元ファイルの `AVURLAsset`（240fps・実速） |
| 同 `.version = .current` | `AVComposition`（通常動画なら `AVURLAsset`）。`tracks[].segments[].timeMapping` の `source` / `target` の長さの比が区間ごとの倍率 |
| `PHImageManager.requestExportSession(forVideo:options:exportPreset:)` | レンダリング版を書き出す `AVAssetExportSession`（Apple のエンジニアがフォーラムで案内している経路。PhotosPicker が渡すものと同じレンダリング版になると見込む） |
| `PHAssetResource`（`.video` / `.fullSizeVideo` / `.adjustmentData`） | 元ファイル / レンダリング版 / 編集情報の生データ。`com.apple.video.slomo` の中身は非公開形式なので**依存しない** |

`PHAsset` に到達するには `PhotosPicker(..., photoLibrary: .shared())` で `PhotosPickerItem.itemIdentifier` を取り、
写真ライブラリの読み取り権限を得る必要がある（[TODO.md](../TODO.md) A の内容そのもの）。
つまり **(B) は TODO A を実装すれば (A) に帰着する**。レンダリング版の可変速をアプリで扱う（区間ごとの倍率を持つ）よりも、
原本を取って倍率 1 にする方が単純で、コマ送りも 1/240 秒になる。

### 3.4 (C) 焼き込み済みスロー

メタデータが無いので、映像の中身から推定するか、ユーザーに指定してもらうしかない。

| 手段 | 仕組み | 精度・適用範囲 | コスト |
| ---- | ------ | -------------- | ------ |
| C-1 スイング所要時間の事前知識 | 検出したダウンスイング長（トップ → インパクト）を「実速なら 0.2〜0.45 秒」と比べて倍率を求め、1 / 2 / 4 / 8 に丸める | 欠測なく検出できていれば 4 倍以上は確実。実速と 1/2 の境目は検出誤差で外れる（下記） | 既存の検出結果から計算できる |
| C-2 コマ複製の検出 | 同一フレームが N 枚連続していれば N 倍スロー | コマ複製で作られたスローだけ。実写 2 本は複製なし（§3.1）。写真アプリのレンダリング版も 1/8 区間は毎フレーム原本が 1 コマ進むので複製は出ない（§3.5） | 隣接フレームの差分（解析時にまとめて取れる） |
| C-3 動きの大きさ・モーションブラー | 1 フレームあたりの移動量や、実速 30fps 特有のブレ | 人物の大きさ・画角・撮影条件に依存し、単独では倍率にできない | — |
| C-4 手動指定 | 実速 / 1/2 / 1/4 / 1/8 を選ぶ | 確実 | UI が要る |

**C-1 の根拠と検証**

- ツアープロのテンポは Tour Tempo の 18/6・21/7・24/8・27/9・30/10（30fps のコマ数で バックスイング / ダウンスイング。すべて 3:1）。
  秒に直すとダウンスイング **0.20〜0.33 秒**、バックスイング 0.6〜1.0 秒。Blast Motion のツアー計測値も
  バックスイング 0.65〜0.85 秒・ダウンスイング 0.23〜0.32 秒（テンポ比 2.5〜3.1 : 1）で一致する
  （[Tour Tempo](https://tourtempo.com/blogs/tips/what-the-numbers-mean)、[Blast Motion](https://blastmotion.com/blog/what-is-golf-swing-tempo-ratio/)）。
  アマチュアはこれより遅くばらつくので、実速のダウンスイングは **0.2〜0.45 秒**を目安にする
- 実速のダウンスイングが 1 秒を超えることは無いので、欠測なく検出できていれば検出値 ≥ 1.0 秒は 4 倍以上のスローと言える
- `docs/data/` の検出結果（[research/260906_1641](./260906_1641-multi-swing-detection.md)）で試算：
  - YouTube Shorts 第 3 候補: ダウンスイング 0.30 秒 → 倍率 1（正しい）
  - Golfboy: ダウンスイング 0.79 秒 → 0.79 ÷ 0.3 = 2.6 → 2 に丸まる。**誤り**（実速の動画。トップ〜インパクトがブレで欠測し、
    トップとインパクトが欠測の両端に置かれて長く出ている。[TODO.md](../TODO.md) D）。
    スイング全体（アドレス → フィニッシュ）2.83 秒で見ても、実速の 1.2〜2.0 秒に対して 1.4〜2.4 倍で曖昧
- したがって、`downswingUnobserved` のときは推定しない（倍率 1 とする）か、推定値を提案として表示するに留める。
  TODO A で 240fps 原本が届くようになれば自分の動画の欠測は減るので、C-1 の対象は実質「お手本側の焼き込みスロー」になる

### 3.5 写真アプリのレンダリング版の速度プロファイル（実測）

E2E ハーネスで合成 240fps 動画（§3.1。スロー区間は写真アプリの既定のまま 0.45〜2.55 秒）を PhotosPicker から取り込み、
アプリの `Documents/Videos/` に保存されたレンダリング版（30fps・14.67 秒・440 フレーム）を調べた。

- メタデータ・トラック情報: フレームレート 30 以外に何も無い（トラックのセグメントも 1 つ）。
  **レンダリング版だけからスロー区間や倍率は分からない**
- 各出力フレームを 240fps 原本のフレームと画素一致で対応付け（時刻が単調増加する制約付き）、
  1 出力フレームあたり原本が何フレーム進むかを数えた（8 = 等速、1 = 1/8）:

| 出力時刻（秒） | 原本時刻（秒） | 1 出力フレームあたりの原本フレーム数 | 速さ |
| -------------- | -------------- | ------------------------------------ | ---- |
| 0.00〜0.55 | 0.00〜0.55 | 8 | 等速 |
| 0.55〜1.03 | 0.55〜0.75 | 7 → 6 → 4 → 3 → 2 → 1 と滑らかに減少 | ランプ（出力で約 0.5 秒） |
| 1.03〜13.87 | 0.75〜2.35 | 1 | 1/8 |
| 13.87〜14.13 | 2.35〜2.47 | 2 → 3 → 4 → 6 と増加 | ランプ（出力で約 0.3 秒） |
| 14.13〜14.67 | 2.47〜3.00 | 8 | 等速 |

合成動画は先頭と末尾の 0.5 秒が静止しているので、その範囲の対応付けは当てにならず、ランプの端の時刻には ±0.05 秒程度の誤差がある。
1/8 区間は原本 1.6 秒 = 出力 12.8 秒で、等速 1.06 秒・ランプ 0.8 秒と足すと 14.67 秒に一致する。

含意：

- 写真アプリの既定では、3 秒の動画のうち **1/8 になるのは中央の約 1.6 秒だけ**。両端 0.5 秒ずつが等速で、その間にランプが入る。
  スイング（実速で 1.2〜2 秒）がこの範囲に収まっていないと、フェーズがランプや等速区間にかかってテンポ比が歪む
- ランプは滑らかに変化するので、区間ごとの固定倍率で近似しても誤差が残る。
  `requestAVAsset(.current)` の `AVComposition` がランプをどう表現しているか（短いセグメントの連続か）は未確認
- 原本があれば上のように画素一致で写像を復元できるが、原本があるなら原本を使えばよい。
  **結論は §3.3 のとおり、レンダリング版は扱わず原本を取る**

## 4. 「x1 = 実速」の実現方針（設計タスクへの入力）

### 4.1 倍率の定義

- 動画ごとに **`slowFactor`**（動画上の秒 ÷ 実世界の秒）を持つ。1 = 実速、8 = 1/8 スロー。既定 1
- 写真アプリのレンダリング版のような可変速は扱わない（原本取得で解消する。§3.3）

### 4.2 再生・同期への影響

| 箇所 | 変更 | 理由 |
| ---- | ---- | ---- |
| `VideoConfig` | `slowFactor` を追加（`decodeIfPresent` で旧データは 1） | 保存形式の後方互換（[AGENTS.md](../AGENTS.md) §5.4） |
| `SyncEngine` | 共通タイムラインを実秒にする（`commonDuration` = 基準側スイング長 ÷ 基準側 `slowFactor`）。`videoTime(at:)` の区間内写像は「区間の何割か」で決まるので式は変わらない | 速度表示の x1 を実速にするため |
| `PlaybackController` | 式は `rate = speed × rateMultiplier` のまま。共通区間長が実秒になるので `rateMultiplier`（動画秒の区間長 ÷ 共通区間長）は基準側で `slowFactor` そのもの、非基準側で「区間長の比 × 基準側の `slowFactor`」になる | 非基準側の倍率は区間長の比に含まれるので、再生に使うのは**基準側の `slowFactor` だけ**でよい（実速 vs 1/8 の組み合わせでも 4 点が一致する） |
| `TransportControlsView` | 速度表示を「x1（実速）」のように実速基準と分かる表記にする | ユーザーが今どの速さで見ているか分かる |
| `PhaseEditView` / `PhaseSet` | `tempoRatio` は比なので不変。秒数を表示する箇所があれば実秒換算 | — |
| `SwingAnalyzer` / `NewComparisonView` | 取り込み時に C-1 の推定（§3.4）を行い、`slowFactor` の初期値にする | — |
| UI | 倍率の手動選択（実速 / 1/2 / 1/4 / 1/8）。置き場所はフェーズ調整シートか比較画面の速度ボタン長押しなど | C-1 は提案に留めるため必須 |

- コマ送りは今までどおり**動画のフレーム単位**（`referenceFrameDuration`）でよい。焼き込みスローの方が細かく送れるのは利点
- 速度プリセット（0.1〜1.0）は実速基準になる。1/8 スロー動画の x0.1 は動画上 0.8 倍で、今の最遅（動画上 0.1 倍）より速くなるが、
  240fps 相当なので 24 コマ/秒で滑らかに見える

### 4.3 実機で確認が要ること

- **8 倍以上の `AVPlayer.rate`**: ローカルファイルは `AVPlayerItem.canPlayFastForward` が true で 2 倍超も再生できるが、
  1080p30 の 8 倍は毎秒 240 フレームのデコードに相当する。実機で滑らかか（フレーム落ちの見え方、発熱）を確認する。
  4K の焼き込みスローは厳しい可能性がある
- 240fps 原本を `rate = 1` で再生したときの表示（60Hz 間引き）とドリフト補正（`driftThreshold` 0.08 秒）の挙動
