# 撮影の停止直前に切り出された「幻のスイング」と、4 秒しか無い「全体の動画」の原因

- 日付：2026-09-13
- 対象：撮影画面（`SwingDuet/Services/Capture/*`）。実機 iPhone 15、2026-09-13 11:17 JST の撮影（ログ `CaptureLogs/20260913-111727.txt`）
- 種別：調査（コードは変えていない）

## 1. 結論

| 症状 | 原因 | 場所 |
| --- | --- | --- |
| 停止ボタンを押しにスマートフォンへ戻る場面が 1 球として切り出された | 停止（flush）ではなく、その 0.1 秒前の通常の検出で出た候補。3 球目のアドレスが直近 8 秒の窓から抜けた瞬間に、3 球目の**インパクトの窪みをアドレス**、フィニッシュで手を高く保った区間をトップ、クラブを下ろした所をインパクト、**カメラへ歩いて体が 2〜3 倍に写った所を「フィニッシュ」**と読んだ。振り上げ・速さは 3 球目のフォローを引き継ぐので素振り判定に掛からず、即決で本番になった | `LiveDetector.observeCandidates`（窓の先頭の扱い）と `SwingDetector.handSamples`（手の高さを窓全体の腰〜首の中央値で正規化する） |
| 「全体の動画」が写真アプリに見当たらない | 残した全体の動画は**最後の区切り 1 本（3.995 秒）だけ**。止める途中（`phase == .stopping`）に 4 球目の切り出しが終わり、その `defer` の `pruneSegments()` が「終わった」扱いで区切り 1〜3 を消した後で、残った 1 本をつないでいる | `CaptureController.pruneSegments`（`.stopping` を finished に含める）と `export` の `defer` |

写真ライブラリに 4 秒の動画として入ったか、アプリ内ファイルに落ちたかはログからは分からない（§4.3）。

## 2. 調べ方

- 実機からの取り出し（`xcrun devicectl device copy from --device 5ACB0436-… --domain-type appDataContainer --domain-identifier com.ha2ne2.SwingDuet`）：
  `Documents/library.json`、`Documents/CaptureLogs/`、`Documents/CaptureTakes/20260913-111727.mov`（33.7 MB）
- `Documents/` の一覧（`xcrun devicectl device info files … --subdirectory Documents`）：`Videos/` に今日のファイルは無い
- Mac で全体の動画に AVFoundation で長さを読み、アプリと同じ `PoseTracker.FrameTracker` を 15fps で掛けて手首・腰・首を出した
  （アプリの `Models/` と `Services/` の純粋計算部分を `swiftc` でそのままリンク。Vision は macOS でも動く）
- 合成の本番スイングの後ろに、上の実測フレームをつないで `LiveDetector` に流し、同じ幻が出るかを見た（§3.4）

### 3.2 なぜ幻が「スイングの形」になるか

`SwingDetector` は手の高さの形「低い → 高い → 低い → 高い」を読む。幻の 4 点は次の通り：

- **アドレス = 3 球目のインパクトの窪み**（27.56）。窓の先頭が本当のアドレス（26.43）を過ぎると、窓の中で最初の「低い区間」がこの窪みになる。
  `windowHeadMargin`（0.3 秒）は「窓の頭で形が欠けた候補」を捨てるだけで、**前のスイングの後半が新しいスイングの前半に化ける**ことは防いでいない
- **トップ = フィニッシュで手を高く保った区間**（29.63）。振り上げ 1.69 は「フィニッシュの高さ − インパクトの高さ」で、本番（中央値 1.87）と変わらない
- **インパクト = クラブを下ろして歩き出した所**（31.57）
- **フィニッシュ = カメラへ歩いて体が大きく写った所**（32.04）。§3.3 の通り、手はフレーム単位では腰の近くにあるが、
  高さは**窓全体の腰〜首の中央値**（打席での大きさ）で割るので、体が 2.7 倍に写れば腰から少し上の手が 0.6（「高い」の閾値 0.5 超）になる
- **ピーク速度 8.65** は幻の範囲（27.56〜32.04）に 3 球目のフォロー（27.56〜27.83）が入るので、本番の速さをそのまま引き継ぐ（中央値 9.17 の 94%）

`SwingDetector` にある「インパクトで手が止まり、その後の動きが下ろしより速ければ次のスイングのアドレス」「フォロー後の下りが上りより速ければ別のスイングのトップ」の 2 つの除外は、
どちらも効かなかった：手を下ろした後は歩き続けて完全には止まらず（`quiet=0`）、幻の「フィニッシュ」の後は人物が枠から消えて「低い」サンプルが無い。
そして `LiveShotJudge.observe` はインパクトの順序しか見ないので、**幻のアドレス（27.56）が 3 球目のフィニッシュ（27.83）より前**でも受け付ける。

打席での腰〜首はログの外接矩形（高さ 0.35）と 30.73 秒の実測（外接矩形 0.46、腰〜首 0.159）から約 0.12 と見積もり、窓の中央値もほぼこれになる（窓の 8 秒の大半が打席）。

### 3.4 合成での再現と限界

合成の本番スイング（15fps、フィニッシュ 1.8 秒保持 → 0.25 秒でクラブを下ろす → 手を低く 0.6 秒）の後ろに §3.3 の実測フレームをつないで `LiveDetector` に流すと、
実機と同じ形の幻（A = 直前のインパクトの窪み、I = 31.6 秒相当、F = 歩いて体が大きく写った所、rise 1.33 / peak 4.20）が登録され、その場で本番と判定された。
ただし合成では「フィニッシュからクラブを下ろす動きがフォローより速い」ことで本番が `SwingDetector` の別スイング除外に掛かって捨てられ、
その結果として窪みがアドレスになる経路だった（この経路では窓なしの後解析でも同じ幻が出る）。実機のログは 3 球目が 33.67 まで観測され続けているので、
実機の経路は「窓の先頭がアドレスを過ぎた」方（§3.1）。合成スイングの速さを実機並みに上げると 15fps では形が崩れて再現できなかった。
再現の材料はスクラッチパッド（`…/scratchpad/sim/main.swift.final`、`…/scratchpad/vision/take-111727-track.txt`）にあり、恒久的なテストにするなら
`LiveDetectorTests` の合成フレームの流儀で「本番 → フィニッシュ保持 → 下ろす → 体が大きく写りながら手は低い → 消える」を書くのがよい。

### 3.5 対策の候補（設計。実装は別タスク）

1. **決まった・登録したスイングの範囲に掛かる候補を受け付けない**（小さく、ライブ限定）：
   `LiveShotJudge.observe` で「アドレスが直前に決めた／保留中の候補のフィニッシュより前」なら捨てる。幻のアドレスは常に前のスイングのインパクトの窪み（フィニッシュより前）なので、
   これだけで今回の幻は消える。窓の先頭を「最後に観測した候補のフィニッシュ＋余白」より前に戻さない形でも同じ効果
2. **体が大きく写り変わるフレームを候補に使わない**（根本。後解析にも効く）：
   腰〜首がその窓（動画）の中央値から大きく外れる（例：1.5 倍以上）か、関節の外接矩形が枠の端に掛かるフレームは検出のサンプルから外す。
   または手の高さをフレームごとの腰〜首（数フレームのメディアン）で正規化する。`SwingDetector` を触るので `docs/data` のサンプル 32 本で `build/analyze-swing` の結果が変わらないことを確かめてから
3. 停止に関して：flush は今回関係なかったが、「人物が枠から消えた後に見つかった候補」を flush で登録しない・停止直前の数秒の候補は判定を待つ、などは幻の別経路への保険になる

推し：1 を先に入れ、2 は後解析と合わせて別途評価する。

## 4. 2 点目：全体の動画が 4 秒しか無い

### 4.1 事実

- ログ：`segment closed` は 17.29 / 25.17 / 30.72 / 34.72 の 4 本（＋停止時に閉じた 34.72〜34.81 の短い 1 本）。しかし `take merged segments=1`
- 実機の `Documents/CaptureTakes/20260913-111727.mov`：**3.995 秒**、1920×1080、HEVC、239.5fps（Mac の AVFoundation で確認）= 区切り 4（30.73〜34.72）そのもの
- 前回（03:11 のログ）は `take merge failed … last segment only` で、こちらも最後の区切りだけ（96 MB ≈ 11 秒）。つまり**全体の動画が全体だったことはまだ一度も無い**

### 4.2 原因

`CaptureController.pruneSegments()` は `phase == .finished || phase == .stopping` を「終わった」と扱い、参照されていない区切りをその場で消す。
`stop()` は最初に `phase = .stopping` にしてから、まだ終わっていない切り出し（`export`）を待つが、`export` の `defer { pruneSegments() }` がこの間に走る。
今回は 4 球目（幻）の切り出しが 34.79 に始まり 34.96 に終わったので、その `defer` が区切り 1〜3（1〜3 球目は判定済みで参照が無い）と停止時の短い 1 本を消し、
残った区切り 4 だけが「全体の動画」としてつながれた。`keepsFullTake` は録画中の間引き（`segmentClosed` 経由）だけを止めており、止める途中には効かない。

4 球目の切り出しが停止より前に終わっていれば（＝停止直前に候補が出なければ）区切りは残り、全体がつながる。1 点目の幻が 2 点目の引き金になっている。

### 4.3 写真ライブラリに入ったか

- ログは `take kept=true` → `take saved index=1 asSwing=false`。`persistVideo` は写真ライブラリへの保存に失敗するとアプリ内ファイルに落とすが、
  現在のログはどちらだったかを書かない（前回のビルドは `source=library(localID: …)` まで書いていた）
- 実機の `Documents/Videos/` に今日のファイルは無い。写真ライブラリに入った場合と、ファイルに落ちた後に起動時の `removeUnreferencedVideos()` で消えた場合の両方と矛盾しない
- 4 球の切り出しは同じ `PhotoLibrary.saveVideo` でアルバム「SwingDuet」に入っている（`library.json` の `assetID` あり）。つないだファイルは `AVMutableMovie` で書いた点だけが違う
- 確かめ方：写真アプリのアルバム「SwingDuet」に 11:17:27 作成の **4 秒**の動画があるか。または Mac で `sudo /usr/bin/log collect --device-udid 00008120-001204143CE3601E --start "2026-09-13 11:17:00"` を取り、`photolibraryd` の 11:18:02 前後を見る
  （今回の調査では root が要るので取っていない）

### 4.4 対策の候補（設計。実装は別タスク）

1. `pruneSegments` の「終わった」を `.finished` だけにする。`stop()` は全体の動画を作った後に `phase = .finished` として `pruneSegments()` を呼んでいるので、止める途中に消す必要は無い
2. `take saved` のログに `source`（library / file）を戻す。帯の「全体の動画も残しました」に秒数（またはつないだ区切りの数）を出せば、4 秒しか無いことにその場で気づける
3. 停止時に閉じた最後の短い区切りは `segmentClosed` を通らずログに出ない。`segment closed` を出しておくと `take merged segments=N` と突き合わせられる

## 5. その他の気づき

- 登録時の範囲 `[26.06, 33.54]` は区切り 3 と 4 にまたがるが、切り出しはインパクトを含む区切り 4 だけから行うので、クリップは 2.8 秒に切り詰められた。
  本物のスイングは「フィニッシュの 1.6 秒後・手が静か」でしか区切らないのでまたがらない前提だが、幻のように長い候補では起きる
