# シークバーで戻るときだけカクつく原因の調査

**作成日時**: 2026-09-12 02:49 JST
**対象**: `SwingDuet/Services/PlaybackController.swift`（`scrub(to:)` / `stepFrame(by:)`）、`SwingDuet/Views/Stage/SeekBarView.swift`、
実機（iPhone 15）に入っている「9/8 20:31」前後のペアの動画ファイル
**目的**: ジョグホイールで戻るのは軽快、シークバーで進むのも滑らかなのに、シークバーで戻るときだけカクつく理由を特定する
**種別**: 調査（コード・設定は変更していない。計測スクリプトはリポジトリに入れていない）

---

## 1. 結論

- 原因は 2 つの事実の組み合わせ。どちらか片方だけでは起きない
  1. **後ろへのシークは、直前のキーフレームから目標までを復号し直す**ので、キーフレームからの距離に比例して遅い
     （Mac で前進 3ms に対し、後退はキーフレーム間隔 120〜160 フレームの動画で 23〜33ms、最大 50ms。§4.2）。
     前へのシークは、いま復号している続きを目標まで進めるだけなので、キーフレーム間隔に関係なく速い
  2. **シークバーはドラッグのイベントごとにシークを出し、前のシークが終わるのを待たない**（`scrub(to:)` → `seekBoth`）。
     `AVPlayer` は新しいシークが来ると走っているシークを取り消して最初からやり直すので、
     シーク 1 回の所要時間がイベント間隔（60Hz の iPhone 15 で 16ms）を超えると、ほとんどのシークが完了せずに絵が出ない（§4.3）
- ジョグホイール（`stepFrame`）は同じ後退シークを使っているが、**前のシークが終わってから最新の位置へ 1 回だけ出す**
  （[ARCHITECTURE.md](../ARCHITECTURE.md) §4 のまとめ待ち）ので、1 回ずつ確実に絵が出て軽快に見える。ジョグとシークバーの差はこれだけ
- 見ていたペアには **YouTube 由来のお手本（キーフレーム間隔 4〜5.3 秒 = 120〜160 フレーム）** が入っている（§2）。
  iPhone で撮った自分のスイング（キーフレーム間隔 29 フレーム）だけなら後退も 7ms で済み、60Hz の連射でも取り消しは起きない（§4.3）。
  お手本が YouTube 由来のとき（このアプリの主な使い方）に必ず踏む
- Mac（M4）でも 60Hz 相当の連射で後退のシークの 40〜70% が取り消され、絵は 11〜23fps に落ちた。実機の A16 は復号が遅い（未計測）ので
  さらに悪い。同じ 2 本を入れればシミュレータ（Mac の復号器を使う）でも再現するはず
- 対策の第一候補は、**スクラブのシークもジョグと同じ方式でまとめる**こと（§7 の A。`PlaybackController` だけの変更）。
  Mac の実測で取り消しが 0 になり、絵の更新は復号の速さそのもの（GOP 160 で 21fps @16ms）まで戻る。
  それでも長い GOP の動画では後退が復号速度で頭打ちになるので、取り込み時にキーフレーム間隔を詰める再エンコード（B）を次の候補として挙げる

## 3. 仕組み：ジョグとシークバーで何が違うか

（図解は [260912_0340-why-jog-smooth-seekbar-choppy.md](./260912_0340-why-jog-smooth-seekbar-choppy.md)）

`PlaybackController` のシークの出し方は 2 通りある。

| 操作 | 呼び出し | 許容 | 前のシークが走っていたら |
| ---- | -------- | ---- | ------------------------ |
| ジョグホイール（`stepFrame`） | `hardSeek` | ゼロ | **待つ**。`seekRequested` を立て、完了ハンドラで最新の位置へ 1 回だけシーク |
| シークバー（`scrub`） | `seekBoth(precise: false)` | 20ms | **待たない**。イベントごとに両プレーヤーへ即シーク |

`SeekBarView` の `DragGesture.onChanged` は指が動いている間、画面の更新に合わせて（iPhone 15 は 60Hz、ProMotion なら 120Hz）呼ばれ、
そのたびに `scrub(to:)` が 2 本のプレーヤーへシークを出す。`AVPlayer.seek` は、完了前に次のシークが来ると前のを取り消す
（完了ハンドラは `finished = false` で呼ばれる）。ARCHITECTURE.md §4 が長押しコマ送りで踏んだ「後のシークが前のを取り消し続けて画面が更新されない」
問題と同じ構図で、`stepFrame` にだけ対策が入っていて `scrub` には入っていない。

前へ進むときにこれが問題にならないのは、前進のシークが 3ms 程度で終わり、次のイベント（16ms 後）より先に必ず完了するから。
後退はキーフレームから復号し直すので、長い GOP の動画では 1 回が 16ms を超え、連射の下では完了できない。

## 4. 実測（Mac M4 / macOS 26.5.2）

`AVPlayer` に `AVPlayerItemVideoOutput` を付けて「新しい絵が出た」時刻を記録し、3 つの出し方で前進と後退を比べた。
1 イベントの移動量は動画の 1 フレーム。実機（A16）の復号は Mac より遅いので、絶対値は実機ではこれより悪い（未計測）。

### 4.1 キーフレーム間隔

`AVAssetReader`（パススルー）で sync sample を数えた。

| 動画 | 映像 | キーフレーム間隔 |
| ---- | ---- | ---------------- |
| マキロイ ドライバー 後ろ（お手本） | H.264 720×1280 29.57fps | 120 フレーム（4.06s）。全 336 フレームに 2 枚 |
| マキロイ ドライバー（お手本） | H.264 1920×1080 29.97fps | 160 フレーム（5.34s） |
| 9/8 20:32 のスイング 2 本（iPhone 撮影） | H.264 1920×1080 30fps | 29 フレーム（0.97s） |
| 参考: `docs/data/yuta_behind.MOV`（iPhone 撮影） | HEVC 1920×1080 30fps | 25〜28 フレーム（0.93s） |
| 参考: `docs/data/YTDown…720p.mp4`（YouTube） | H.264 640×640 30fps | 全 205 フレームに 1 枚 |

iPhone のカメラは約 1 秒ごと、YouTube 由来は 4〜7 秒ごと。

### 4.2 1 回ずつ完了を待つシーク（ジョグと同じ出し方）

許容ゼロで 1 フレームずつ 60 回。「絵が出るまで」はシークを出してから新しい絵が出るまでの時間。

| 動画 | 前進（中央値 / p90 / 最大） | 後退（中央値 / p90 / 最大） |
| ---- | ---- | ---- |
| マキロイ 後ろ（GOP 120） | 3.7 / 4.7 / 6.2 ms | **24.0 / 30.9 / 38.0 ms** |
| マキロイ 横（GOP 160） | 3.8 / 4.7 / 7.1 ms | **34.2 / 46.0 / 52.6 ms** |
| 9/8 20:32 のスイング（GOP 29） | 5.6 / — / — ms | 8.4 / 14.9 / — ms |
| yuta_behind（GOP 28） | 2.9 / 6.7 ms | 6.0 / 12.0 ms |
| YouTube 640×640（GOP 205） | 2.9 / 4.7 ms | 12.9 / 17.0 / 32.0 ms |

後退の所要時間はキーフレームからの距離に比例する。YouTube 640×640 を 4 フレームずつ戻したときの推移（キーフレームは 0.03s のみ）：

```
t=6.17s 36ms   t=5.10s 15ms   t=4.03s 12ms   t=2.97s 9ms   t=1.90s 6ms   t=0.97s 3.5ms
```

前進はどの動画でも 3〜4ms で一定。ジョグが後退でも軽快なのは、この 24〜34ms（実機ではもっと長い）を 1 回ずつ待って
確実に絵を出しているから。

### 4.3 完了を待たずに連射するシーク（シークバーと同じ出し方）

許容 20ms、一定間隔で 60 回出し続け、完了した数と実際に出た絵の数を数えた。16ms が iPhone 15（60Hz）のドラッグイベント間隔、
8ms が ProMotion、4ms は復号が遅い実機の代わり（間隔に対して復号が相対的に遅い状況）。

| 動画 | 間隔 | 前進：完了 / 絵（fps） | 後退：完了 / 取り消し / 絵（fps） |
| ---- | ---- | ---- | ---- |
| マキロイ 後ろ（GOP 120） | 16ms | 60 / 60（40） | 35 / **25** / 35（23） |
| | 8ms | 60 / 60（59） | 15 / **45** / 15（15） |
| | 4ms | 59 / 59（77） | 2 / **58** / 2（2.6） |
| マキロイ 横（GOP 160） | 16ms | 60 / 60（40） | 17 / **43** / 17（11） |
| | 8ms | 60 / 60（59） | 2 / **58** / 3（3.0） |
| | 4ms | 56 / 60（78） | 1 / **59** / 1（1.3） |
| 9/8 20:32 のスイング（GOP 29） | 16ms | 60 / 52（35） | 60 / 0 / 59（39） |
| | 8ms | 60 / 52（51） | 32 / 28 / 33（33） |
| | 4ms | 36 / 34（44） | 3 / 57 / 3（3.9） |

- 前進は 60Hz でも 120Hz でも全部完了する。後退は 1 回の所要時間が間隔を超えた途端に取り消しが積み上がり、
  絵の更新が数 fps まで落ちる。これが「シークバーで戻るときだけカクカク」の正体
- 取り消されたシークは途中まで復号した分も捨てられる（4ms 間隔で GOP 160 の動画は 768ms 走らせて絵が 1 枚しか出ない）。
  連射している限り絵が出ないので、指を止めた瞬間にだけ飛ぶ
- iPhone 撮影のスイングだけなら 60Hz の連射でも取り消し 0。お手本が長い GOP のときに顕在化する

### 4.4 連射をまとめた場合（対策 A の見込み）

同じ連射でも「走っていなければ即、走っていれば完了時に最新の位置へ 1 回」（`stepFrame` と同じ）にすると：

| 動画 | 間隔 | 連射のまま：絵（fps） | まとめる：出した数 / 取り消し / 絵（fps） |
| ---- | ---- | ---- | ---- |
| マキロイ 後ろ（GOP 120） | 16ms | 23 | 52 / 0 / 42（**28**） |
| | 8ms | 15 | 19 / 0 / 19（**19**） |
| | 4ms | 2.6 | 10 / 0 / 10（**13**） |
| マキロイ 横（GOP 160） | 16ms | 11 | 32 / 0 / 31（**21**） |
| | 8ms | 3.0 | 14 / 0 / 14（**14**） |
| | 4ms | 1.3 | 8 / 0 / 8（**10**） |

取り消しが 0 になり、絵の更新は「復号にかかる時間の逆数」まで戻る。ただしそれが上限なので、長い GOP の動画の後退は
Mac でも 10〜28fps、実機ではそれ以下に留まる（滑らかさの上限は B で上げる）。

## 5. 実機で顕著な理由

- A16 の H.264 復号は M4 より遅い（倍率は未計測）。§4.2 の後退 24〜34ms が実機で 16ms を超えているのは、Mac ですでに超えていることから確実
- 2 本のプレーヤーが同時に後退シークを出すので、復号器を取り合う。長い GOP の側がボトルネックになる
- iPhone 15 は 60Hz なので間隔は 16ms。ProMotion 端末では 8ms になり、さらに悪化する

## 6. 実機での確認手順（コード変更なし）

1. **お手本を iPhone 撮影の動画に替える**（キーフレーム間隔 1 秒）→ シークバーの後退も滑らかになれば、長い GOP が条件であることの確認
2. **自分基準とお手本基準を切り替える** → 変わらないはず（基準はシークの出し方に関係しない）
3. **シミュレータに同じ 2 本を入れる**（[e2e-simulator](../../.claude/skills/e2e-simulator/SKILL.md) の手順で投入）→ Mac の復号器で §4.3 が再現するか
4. 必要なら実装タスクとして `seek` の完了ハンドラに `finished` と所要時間のログを一時的に入れ、実機の後退 1 回の所要時間と取り消し率を測る（§5 の未計測値）

## 7. 対策の選択肢（実装は別タスク。本調査では変更しない）

| 案 | 内容 | 効果（Mac 実測） | 留意点 |
| -- | ---- | ---------------- | ------ |
| **A. スクラブのシークをまとめる** | `scrub(to:)` を `stepFrame` と同じ「走っていなければ即、走っていれば完了時に最新位置へ 1 回」にする。`seekRequested` の仕組みをスクラブにも使えるよう一般化（許容 20ms のまま） | 取り消し 0。後退 2.6→13fps、11→21fps（§4.4） | `PlaybackController` だけの変更。前進や ProMotion の取りこぼしも同時に直る。後退の上限は復号速度のまま |
| **B. 取り込み時にキーフレーム間隔を詰める** | `AVAssetWriter` で再エンコード（`AVVideoMaxKeyFrameIntervalKey` 15〜30、または `…IntervalDurationKey` 0.5〜1s）。sync sample を数えて長い GOP のファイルだけ対象にする | 後退 1 回の上限が 15〜30 フレーム分に（iPhone 撮影と同じ 7〜8ms） | 取り込みが数秒〜十数秒延びる（30s 1080p）。再エンコードで画質とファイルサイズが変わる。いまのパススルー（音声落とし）と統合し、既存ファイルの移行が要る |
| C. スクラブ中だけ `toleranceBefore` を大きくして手前のキーフレームに落とす | シークは速くなる | 絵が 4〜5 秒単位で飛ぶので不可 | — |
| D. 自前で復号してフレームをキャッシュ | `AVAssetReader` で前後数十フレームを保持 | 後退も前進と同じ速さ | 実装が大きくメモリを食う。`AVPlayer` と二重の再生系になる |

**推奨は A + B**。A は必要条件だが単独では後退が復号速度で頭打ちになり、iPhone の 240fps 原本もキーフレーム間隔が約 1 秒（235 フレーム）で同じ問題を持つ。
選択肢の比較と B の実測（サイズ・画質・変換時間）は [260912_0319-scrub-friendly-media-options.md](./260912_0319-scrub-friendly-media-options.md) にまとめた。
A は数十行で、ARCHITECTURE.md §4 に書いてあるコマ送りの方針をスクラブへ広げるだけ。B は取り込みの設計変更と既存ファイルの移行を伴う。

## 8. 計測方法（再現用）

Mac 上の Swift スクリプト 2 本（`swiftc` でビルド。リポジトリには入れていない）。

- **gop**: `AVAssetReader`（`outputSettings: nil`）で全サンプルを読み、`kCMSampleAttachmentKey_NotSync` からキーフレームの位置と間隔を出す
- **seekbench**: 1 つの `AVPlayer` に `AVPlayerItemVideoOutput` を付け、2ms 間隔で `hasNewPixelBuffer` を見て新しい絵の時刻を記録する。
  `step`（完了を待って次を出す。所要時間の分布）、`scrub`（一定間隔で出し続ける。完了数・取り消し数・絵の数）、
  `coalesce`（同じ間隔で位置だけ更新し、走っていないときだけ最新位置へシーク）の 3 モードを、前進・後退、フレーム数、開始位置、間隔で切り替える

実機の動画は `xcrun devicectl device copy from --domain-type appDataContainer --domain-identifier com.ha2ne2.SwingDuet` で取り出した
（`Documents/library.json` と `Documents/Videos/`）。
