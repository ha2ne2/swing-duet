# 実機でお手本動画だけがカクつく原因の調査

**作成日時**: 2026-09-07 02:54 JST
**対象**: `SwingDuet/Playback/PlaybackController.swift`（ドリフト補正・ループ復帰・再生開始）と `docs/data/` のサンプル動画 2 本
**目的**: シミュレータでは 2 本とも滑らかなのに、実機ではお手本（マキロイ、YouTube 由来）だけがカクつく理由を特定する。
同期はお手本基準で使っている
**種別**: 調査（コード・設定は変更していない。計測スクリプトはリポジトリに入れていない）

---

## 1. 結論

- 原因は「お手本という役割」ではなく、**お手本の動画ファイルに音声トラックがあること**。自分側（Golfboy 書き出し）には音声が無い
- 音声トラックのある `AVPlayerItem` は、`rate` を設定してから、またはシークのたびに、**プレーヤーの時計（`currentTime`）が
  100〜215ms 止まる**（音声レンダラの起動待ち。`isMuted = true` でも起きる。Mac 上で実測）。
  `PlaybackController.correctDrift` はこの止まった分を「ドリフト」と見なし、80ms を超えるとシークで補正する。
  そのシークがまた音声を起動し直して時計を止めるので、**シークが連鎖してフレームが飛び飛びになる**（§4）
- 連鎖が起きる条件は **「止まる時間 × 再生速度 > 80ms」**。Mac ではシーク後の停止が約 215ms なので、x0.5 以上で連鎖し、
  既定の x0.3 は 64ms でぎりぎり下回る（だからシミュレータでは滑らかに見える）。実機は音声セッションの起動が重く停止が長いため、
  x0.3 でも閾値を超えて連鎖している、というのが最も有力な説明（§5。実機の停止時間そのものは未計測）
- 音声トラックを外す（`AVPlayerItemTrack.isEnabled = false`、または映像だけの合成）と、x1.0 でもシークが 0 回になり
  Golfboy と同じ滑らかさになる。逆に Golfboy の映像にマキロイの音声を付けると同じ連鎖が再現した（§3.3）
- キーフレーム間隔（マキロイ動画は 6.8 秒で実質 1 枚）は疑ったが、Mac ではシーク所要時間に差が無く（どちらも中央値 18ms）、主因ではない（§3.4）
- 副次的な発見: 音声付きの動画は連鎖しない速度でも、共通タイムラインより常に 30〜64ms（1〜2 コマ）**遅れて**再生されている。
  滑らかに見えても同期が 1〜2 コマずれている（§6）

---

## 2. 再生の仕組みと疑った箇所

`PlaybackController` は `CADisplayLink` の共通時刻を親クロックにし、2 つの `AVPlayer` を `rate` で走らせる。
毎 tick（60Hz）で「期待する動画時刻」と `player.currentTime()` を比べ、差が 80ms を超えると許容 20ms のシークで補正する
（[ARCHITECTURE.md](../ARCHITECTURE.md) §4）。基準側と非基準側でコードパスが分かれるのは区間倍率（基準側は常に 1.0）だけで、
役割の違いでカクつく仕組みは無い。したがって差は動画ファイルの性質か、実機だけで効く要因のどちらかにある。

シークが起きるのは次の場面。連鎖の起点になりうる。

| 場面 | 呼び出し | 許容 |
| ---- | -------- | ---- |
| 再生開始（`play`）、一時停止、ジャンプ、コマ送り、スクラブ終了、基準・フェーズの変更 | `hardSeek` | ゼロ |
| ループの先頭へ戻る（毎 tick の `tick` 内） | `hardSeek` + `applyRates` | ゼロ |
| ドリフト補正（毎 tick） | `correctDrift` | 20ms |

`hardSeek` はシークの完了を待たずに `rate` を設定し、DisplayLink はその瞬間から共通時刻を進める。
シーク中にプレーヤーの時計が止まっていれば、その分がそのままドリフトになる。

## 3. 実測

### 3.1 サンプル動画 2 本の性質

`AVAssetReader`（パススルー）で全サンプルを読み、sync sample・表示時刻・トラック構成を出した（Mac、AVFoundation）。

| | 自分（`Golfboy_FormMovie (16).mp4`） | お手本（`YTDown.com_..._720p.mp4`） |
| -- | -- | -- |
| 映像 | H.264 High 4.0、1440×1080、4.3 Mbps | H.264 Main 3.1、640×640、0.47 Mbps |
| フレームレート | 30.9（間隔 0.0317 / 0.0333 秒の混在） | 30.0 |
| キーフレーム | 30 フレームごと（9 枚） | **先頭 1 枚のみ**（frames 0 / 1 と末尾 206〜208。GOP 205 フレーム = 6.8 秒） |
| B フレーム | あり | あり |
| **音声** | **なし** | **AAC 127 kbps** |

実機に入れた動画がこの 2 本と同じ（写真アプリ経由で再エンコードされていない）ことは未確認だが、
YouTube 由来の動画に音声が付き、Golfboy 書き出しに音声が無いのは出所からして同じはず。

### 3.2 ドリフト補正ループの模擬（Mac）

アプリと同じロジック（60Hz tick、閾値 80ms、許容 20ms のシーク、精密シーク直後に `rate` 設定、途中でループ先頭へ精密シーク）を
1 プレーヤーで動かし、`AVPlayerItemVideoOutput` で実際に新しいフレームが出た時刻を記録した。
「フレーム間隔」が期待値（1/30 秒 ÷ 速度）の 1.8 倍を超えた回数がカクつきの直接の指標。

| 動画 | 速度 | `rate` 設定後に時計が進み始めるまで | 補正シーク回数 | フレーム間隔（中央値 / 最大） | 1.8 倍超 |
| ---- | ---- | ---- | ---- | ---- | ---- |
| Golfboy | x0.3 | 18〜35ms | 0 | 106 / 131ms（期待 111） | 0 |
| Golfboy | x1.0 | 18〜35ms | 0 | 35 / 72ms（期待 33） | 0〜1 |
| マキロイ | x0.2 | 107ms | 0 | 161 / 355ms（期待 167） | 1 |
| マキロイ | x0.3 | 105ms | 0 | 107 / 264ms（期待 111） | 2（ループ復帰時） |
| マキロイ | x0.5（ループあり） | 104ms | **14 / 5 秒** | 71 / 181ms（期待 67） | **14** |
| マキロイ | x1.0 | 87〜106ms | **45 / 4 秒** | **70 / 175ms**（期待 33） | **33 / 57** |

マキロイ x1.0 のドリフトの推移（抜粋）。シークで戻しては止まり、また 80ms を超えてシーク、を繰り返している。

```
t=18ms drift=-18  t=34 -34  t=52 -52  t=70 -70  t=87 -82 → seek
t=105ms drift=-18  t=123 -36  t=141 -54  t=159 -72  t=176 -89 → seek
t=193ms drift=-17  ...（以下同じ）
```

再生中にシーク（ループ復帰・強制シーク）したあとの停止時間: マキロイは約 **215ms**（x0.3 でドリフト −64ms に達して止まる）、
Golfboy は 0（ドリフトが変わらない）。再生開始時の停止（約 105ms）より、再生中のシーク後の方が長い。

### 3.3 音声トラックの切り分け

| 条件 | 速度 | 時計が進み始めるまで | 補正シーク | 1.8 倍超 |
| ---- | ---- | ---- | ---- | ---- |
| マキロイの映像だけを合成（`AVMutableComposition`） | x1.0 | 18ms | 0 | 0 |
| マキロイの音声トラックを `isEnabled = false` | x1.0 | 18ms | 0 | 0 |
| 同上、x0.3 でループ復帰 | x0.3 | 35ms | 0 | 0（復帰後のドリフト −7ms） |
| 同上、x1.0 でループ復帰 | x1.0 | 17ms | 0 | 0 |
| **Golfboy の映像 + マキロイの音声** | x1.0 | 108ms | **28 / 2.5 秒** | **20 / 39** |
| Golfboy の映像 + マキロイの音声、ループ復帰 | x0.3 | 105ms | 0 | 0（復帰後 −65ms。マキロイと同じ） |

音声トラックの有無だけで、症状が両方向に入れ替わる。

### 3.4 キーフレーム間隔（GOP）の影響

音声を外したマキロイ動画に 500ms ごとに許容 20ms のシークを強制し、シークから新しいフレームが出るまでを測った。

| 動画 | シーク → 新フレーム（中央値 / 最大） |
| ---- | ---- |
| マキロイ（映像のみ、GOP 205） | 18 / 36ms |
| Golfboy（GOP 30） | 18 / 36ms |

Mac（Apple Silicon）では先頭キーフレームから 100 フレーム以上復号し直しても差が出ない。実機のデコーダで多少伸びる可能性はあるが、
主因は音声側と見る。

## 4. 仕組み（なぜ連鎖するか）

1. `play()` またはループ復帰で `hardSeek` → 即 `rate` 設定。音声付きアイテムは音声レンダラの起動（実機なら音声セッションの
   有効化も）を待つあいだ `currentTime` が止まる。共通時刻は DisplayLink で進み続ける
2. 止まった時間 × 速度 がドリフトになる。80ms を超えると `correctDrift` がシーク
3. シークは音声レンダラを再起動するので、また時計が止まる（Mac で約 215ms）。その間に再びドリフトが 80ms を超え、次のシーク
4. 以後、シーク → 停止 → 閾値超え → シーク、を tick ごとに繰り返す。画面は「止まって飛ぶ」の連続になる

連鎖の条件は **停止時間 × 速度 > 80ms**。Mac の 215ms なら速度 0.37 以上で連鎖する（x0.5 / x1.0 が該当、x0.3 は 64ms で回避）。
この条件を満たさない速度でも、停止時間の分だけ音声付きの側が常に遅れて再生される（§6）。

---

## 5. 実機とシミュレータで差が出る理由（仮説）

シミュレータは Mac の CoreAudio（すでに動いている）をそのまま使うが、実機では次の要因で停止時間が伸びると考えられる。
いずれも実機で未計測。

- **音声セッションの有効化**: アプリは `AVAudioSession` を設定していない。音声付きプレーヤーを最初に動かした時点で既定カテゴリで
  セッションが有効化される。実機では audio server との往復・出力経路の決定が入り、Bluetooth 出力（AirPods 等）だと更に長い
- **シークごとの音声レンダラの再起動**が実機では重い（§3.2 の 215ms が実機では 267ms を超えれば、既定の x0.3 でも連鎖する）
- 先頭キーフレームからの復号し直し（§3.4）は Mac では無視できたが、A 系チップのデコーダでは多少伸びる可能性がある。副次要因
- 低電力モード・発熱で上記が伸びる

x0.3 がちょうど閾値付近（Mac で余裕 16ms）なので、実機ではわずかな差で連鎖側に落ちる。

## 6. 副次的な発見：音声付きの側は同期が 1〜2 コマ遅れる

連鎖が起きない速度でも、音声付き動画は再生開始後 30ms（x0.3）、ループ復帰後 64ms（x0.3）遅れたまま走り続ける（§3.2 のドリフト推移）。
80ms 未満なので補正されず、自分側の動画に対してお手本が 1〜2 コマ遅れてインパクトを迎える。「滑らかだが少しずれる」状態。
原因は同じなので、音声トラックを外せば同時に解消する（§3.3 で復帰後のドリフトは −7ms）。

## 7. 実機での確認手順（コード変更なし）

1. **基準を「自分基準」に切り替える** → カクつきがマキロイ側に残れば、役割ではなくファイルの問題（本調査の予測: 残る）
2. **速度を変える**: x0.1 / x0.2 では滑らか、x0.5 / x1.0 で悪化するなら §4 の閾値説と一致。ループ復帰の直後から始まるかも見る
3. **シミュレータで x1.0 にする**: Mac の実測どおりならシミュレータでも連鎖する。実機固有ではないことの確認になる
4. **音声を外した同じ動画で比べる**: 映像だけを書き出した版（Mac で `AVAssetExportSession` のパススルーで作れる。本調査の
   スクリプトを流用可能）を実機に入れ、カクつきが消えるか
5. 必要なら実装タスクとして `correctDrift` にシーク回数と停止時間のログを一時的に入れ、実機の停止時間を測る（§5 の未計測値）

## 8. 対策の選択肢（実装は別タスク。本調査では変更しない）

アプリは音声を一切使わない（`isMuted = true`、[SPEC.md](../SPEC.md) に音声要件なし）ので、音声トラックを再生パイプラインから外すのが筋。

| 案 | 内容 | 利点 | 留意点 |
| -- | ---- | ---- | ------ |
| A. 再生時に音声トラックを無効化 | `AVPlayerItem.status == .readyToPlay` 後に `tracks` の音声を `isEnabled = false`（§3.3 で効果を確認） | ファイルを触らない。既存の保存データもそのまま | `tracks` は readyToPlay 後にしか取れないので status の監視が要る。`PhaseEditView` のプレーヤーにも同じ処置 |
| A'. 映像だけの合成で再生 | `AVMutableComposition` に映像トラックだけ入れて `AVPlayerItem(asset:)`（§3.3 で効果を確認） | 生成時に同期的に済む | duration が合成側の値になる。`videoTime` の写像や `PhaseEditView` の読み出しとの整合を確認 |
| B. 取り込み時に音声を捨てる | `AVAssetExportSession`（パススルー）で映像だけの mov にして `Documents/Videos/` へ | 再生側のコードが単純なまま。以後どの経路でも音声が混ざらない | 取り込みが数百 ms〜数秒延びる。既存の保存済み動画には効かない（移行が要る） |
| C. ドリフト補正の堅牢化 | シークや `rate` 変更の直後 200〜300ms は補正しない、または `setRate(_:time:atHostTime:)` で開始時刻を予約する | 将来また音声付き入力が来ても連鎖しない | 単独では不十分（停止 215ms のヒッチはループ復帰ごとに残る）。A / B と併用する価値はある |

**推奨は B に C の「シーク中は補正しない」を添える**（§6 の 1〜2 コマ遅れも同時に消える）。理由と B の実測：

- 原因（音声トラック）を入口の 1 か所で断てる。再生側は `PlaybackController` の 2 本、`PhaseEditView` の 1 本、サムネイル、
  解析器がすべて同じ「映像だけのファイル」を読むので、プレーヤーごとの処置（A / A'）や readyToPlay の監視が要らず、
  将来プレーヤーを増やしても再発しない。YouTube のダウンロード・画面収録など音声付きの入力は今後も来る
- 映像トラックだけの `AVMutableComposition` を `AVAssetExportPresetPassthrough` で書き出すと、再エンコード無しで
  **マキロイ動画 26ms、Golfboy 4ms**（Mac）。フレーム数と表示時刻は完全に一致し（最大差 1.6e-5 秒。Golfboy の可変間隔も保持）、
  `preferredTransform`（回転）も引き継げる。取り込み → 解析の流れ（`StageView.load` → `ProjectStore.importVideo`）に
  1 ステップ足すだけで、解析中の表示に埋もれる
- 既存の `Documents/Videos/` は起動時に 1 度だけ走る移行（音声トラックがあるファイルを書き出して置き換え）で揃える
- C は「シーク直後 N ms」の決め打ちではなく、`seek(completionHandler:)` の完了までその側の補正を止める形にする。
  値の根拠が要らず、実機でシークが遅い動画（長い GOP の 4K など）でも連鎖しない

## 9. 計測方法（再現用）

Mac 上の Swift スクリプト 2 本（`swiftc` でビルド。リポジトリには入れていない）。

- **probe**: `AVAssetReader` パススルーで sync sample・表示時刻・サンプルサイズを集計し、トラック構成と codec を出す
- **sim**: 1 つの `AVPlayer` に `AVPlayerItemVideoOutput` を付け、アプリと同じドリフト補正ループを回す。
  オプションで「精密シークを待たずに rate 設定」「途中でループ復帰」「音声トラックを外す / 無効化 / 別ファイルの音声を合成」
  「一定間隔で強制シーク」を切り替え、補正シーク回数・時計が進み始めるまでの時間・フレーム間隔の分布を出す

同じ手順を実機で行うには、アプリ内に一時的なログを入れるか、上記ロジックを iOS の検証アプリに移す必要がある。
