## 0. 結論

1. **「前向き・後ろ向きの 2 パス」は要らない。** いまの Savitzky–Golay は対称な畳み込みで、もともと位相の遅れが無い
   （全 7 候補・全動画で遅れ 0 コマを実測）。往復させる意味があるのは片方向の（因果的な）フィルタで、ここは該当しない。
   「2 パス」は実質「窓を広げる」ことなので、**どこまで広げるか**の判断に読み替える
2. **最も効くのは「描く曲線を、点を通る曲線から点の近くを通る曲線に変える」**（§7 案 A）。
   いまの Catmull–Rom は測定点を必ず通るので、ブレがそのまま角になる。一様 3 次 B スプライン（点は制御点、通過しない）にすると
   曲がりの揺れが **2.47° → 1.74°**、90% 値は **9.29° → 4.48°** と半減する。保存データも形式の版も変えず、
   直すのは `JointTrailOverlay.curve(through:)` の式だけ
3. **次に効くのは Whittaker（罰則付き）平滑化**（§7 案 B）。「運動は急に折れ曲がらない」を式にして曲線を当てはめる。
   λ=10 で 2.47° → 1.45°。欠けたコマを自然に埋められ、Vision の信頼度で重み付けもできる。案 A と併せると 1.22°
4. 局所フィルタの範囲では「間引きを平均にする」（§6）が効くが、上の 2 つより小さい（−12〜23%）。
   保存する平滑化を SG5 ×2 に強めるのは、描く線では 10% しか変わらず薄い
5. **「スローほど不利」は理屈としては正しいが、実測では裏付けが取れなかった**（§5）。窓がコマ数なので実時間で見ると
   スローほど均せていないのは確かだが、1 コマの歩幅に対する振動の比は速さによらず 0.28〜0.36 で並ぶ。
   窓を速さに比例させる案は「試す価値のある仮説」であって、原因と断定はできない
6. **検出（`SwingDetector`）に使う手首の系列には掛けない。** 掛けると macroy_behind が**検出失敗**になる（§8）。
   得られるものはフェーズが 0.03 秒動く程度しかない
7. 頭の軌跡を消す（TODO L の 2）は、部位の削除と保存形式の版上げだけで、平滑化の話とは独立（§9）

## 1. いま何が起きているか

`JointTrails.smoothed()` は 5 点の Savitzky–Golay を 1 回だけ掛ける。手首側には `PoseTracker.medianFilteredWrists`（3 点メディアン）もある。

| 平滑化 | 振動 中央 / 90% | 元からのずれ 中央 / 最大 | 遅れ | トップ付近 | インパクト付近 | 道のり比 |
| --- | --- | --- | --- | --- | --- | --- |
| なし | 1.87 / 5.30 | — | 0 | — | — | 1.000 |
| **SG5 ×1（いま）** | **0.99 / 2.79** | 0.53 / 13.19 | 0 | 12.00 | 2.66 | 0.973 |
| SG5 ×2 | 0.81 / 2.38 | 0.46 / 13.51 | 0 | 11.99 | 2.64 | 0.955 |
| SG5 ×3 | 0.66 / 1.99 | 0.54 / 15.51 | 0 | 13.74 | 2.88 | 0.947 |
| SG7 ×1 | 0.68 / 1.93 | 0.64 / 17.89 | 0 | 15.67 | 3.38 | 0.954 |
| SG9 ×1 | 0.55 / 1.49 | 0.83 / 20.64 | 0 | 18.31 | 3.60 | 0.936 |
| メディアン3 → SG5 ×2 | 0.81 / 2.38 | 0.46 / 13.53 | 0 | 12.04 | 2.64 | 0.953 |
| SG5 ×1 → 3 点の箱型 | 0.58 / 1.63 | 0.61 / 16.47 | 0 | 14.43 | 3.12 | 0.932 |

**この表は全コマ（235 点）の系列で測ったもので、画面に出る線とは別物**であることに注意する。
描くときは 80 点まで間引く（`JointTrailOverlay.thinned`）ので、見えるのは 3 コマに 1 点の折れ線になる。
判断には §6 の「描く線」の値を使う。

画面での大きさの目安（概算・未実測）：ペインは人物が収まるように拡大するので、体の高さ（腰〜首）はおよそ 250〜300pt になる。
体の高さの 1% は 3pt 前後で、これが線のギザギザとして見える。

## 2. 遅れは無い（往復は不要）

7 候補すべて、4 本すべてで「生の系列と最も一致する時間のずらし」は **0 コマ**だった。Savitzky–Golay は左右対称な重みなので当然で、
往復（前向き → 後ろ向き）を持ち出す必要はない。**SG を 2 回掛けることは、重みを畳み込んだ 1 つの広い対称窓と同じ**。
つまり選ぶべきは「往復するか」ではなく「窓をどれだけ広げるか」。

## 3. 掛けすぎの代償

- **トップ・インパクト付近のずれ**：macroy_behind（後方・1/2 スロー、弧の折り返しが鋭い）で、トップ付近の最大のずれは
  SG5 ×1 で 1.14、×2 で 1.44、SG7 で 2.11、SG9 で 2.32（体の高さの %）。SG5 ×2 までは 0.3 の増加で収まる
- **道のり比**は部位で読み方が違う。手は 0.97 → 0.95（弧が少し短くなる）だが、**肩は 0.79 → 0.74**。
  肩はほとんど動かないので「道のり」の大半が振動そのもので、短くなるのは望ましい方向。近い将来「弧の長さ」を数字で出すなら、
  平滑化の強さで値が変わることに注意が要る
- 報告の動画のトップ付近のずれが 12 と大きいのは、生の点にトップ付近で大きな外れ値があり、どのフィルタもそれを寄せているため
  （窓を広げても 12 → 18 とゆるやかにしか増えない）

## 4. 部位で必要な強さが違う

報告の動画（振動の中央値）：

| 部位 | なし | SG5 ×1 | SG5 ×2 | SG9 ×1 |
| --- | --- | --- | --- | --- |
| 手 | 1.87 | 0.99 | 0.81 | 0.55 |
| 左肩 | 1.53 | 0.78 | 0.57 | 0.38 |
| 左股関節 | 0.95 | 0.43 | 0.31 | 0.23 |

肩・股関節はほとんど動かないので強く掛けても壊れるものが無く、SG5 ×2 で 0.3〜0.6 に収まる。
手だけが弧の形を持つので、強さを分けるなら「手は控えめ、肩・股関節は強め」が理にかなう。

## 5. 「スローほど不利」は裏付けが取れなかった

理屈はこうなる：解析は常に 30fps に間引くので 5 点の窓は**動画時間で 0.17 秒**。1/2 スローなら実時間 0.083 秒、
1/8 スローなら 0.021 秒しか均していない。姿勢推定の揺れはコマごとに独立に乗るから、スローほど不利なはず。

実測（手・体の高さ = 1 の %。歩幅は隣り合うコマの移動量の中央値、振動は SG5 ×1 の後の 2 階差の中央値）：

| 動画 | 速さ | 歩幅 | 振動 | 比 |
| --- | --- | --- | --- | --- |
| 報告の動画 | 1/2 | 2.90 | 0.99 | 0.34 |
| macroy_behind | 1/2 | 1.97 | 0.71 | 0.36 |
| yuta_behind | 1/4 の素材 | 3.70 | 1.98 | 0.54 |
| IMG_0172（夜・実速） | 1/1 | 10.38 | 2.92 | 0.28 |
| IMG_0186_05（実速） | 1/1 | 1.26 | 0.37 | 0.29 |

**歩幅に対する振動の比は速さで並ばない**（0.28〜0.36、夜の yuta だけ 0.54）。線の見た目のギザギザは「振動 ÷ 歩幅」で決まるので、
この範囲ではスローが不利とは言えない。振動の絶対値が大きい IMG_0172 は実速だが歩幅も大きく、比では最も小さい。

つまり窓を速さに比例させる案（`VideoConfig.effectiveSlowFactor` を使えば軌跡を作る時点で分かる）は**試す価値のある仮説**だが、
いま見えている振動の原因と断定はできない。確かめるなら、同じスイングを実速とスローで撮り比べるのが早い（未実施）。
実際に効いたのは曲線の作り方（§7）と間引き（§6）なので、順序としてはそちらが先。

## 6. 描くときの間引きを平均にする（保存は変えない）

`JointTrailOverlay` は 1 本の線を 80 点まで**等間隔に間引いて**描く（240fps 原本で曲線が 1 万区間になるのを防ぐため）。
いまは「3 点に 1 点を採る」なので、採った点に乗ったブレがそのまま線に出る。これを**「3 点の平均を採る」**に変えたときの、
**実際に描かれる折れ線**の曲がり具合（隣り合う描画点 3 つの 2 階差。体の高さ = 1 の %）：

| 動画 | 間引き | 保存 SG5 ×1（いま） 中央 / 90% | 保存 SG5 ×2 中央 / 90% |
| --- | --- | --- | --- |
| 報告の動画（235 → 79 点） | 採る | 4.05 / 11.62 | 3.65 / 11.00 |
| 同 | **平均** | **3.10 / 8.96** | 2.98 / 8.33 |
| macroy（214 → 72 点） | 採る | 3.07 / 20.16 | 3.19 / 20.59 |
| 同 | **平均** | **2.69 / 17.18** | 2.62 / 17.86 |
| IMG_0186_05（108 → 54 点） | 採る | 0.89 / 1.99 | 0.90 / 2.00 |
| 同 | **平均** | 0.89 / 1.93 | 0.79 / 1.67 |

平均にすると 12〜23% 下がる。保存データも版も変えず、間引きが要らない短い線（IMG_0172 の 36 点、yuta の 27 点）には何も起きない。
**保存の平滑化を強めても描く線はあまり変わらない**（macroy では ×2 の方がわずかに悪い）ので、順序としてはこちらが先。

## 7. 「連続した運動」として曲線を作る（局所フィルタの外の案）

ここまでは「点列を局所的に均す」話だったが、スイングは連続した運動なので、**滑らかな曲線を当てはめる**という筋がある。
画面に出る曲線まで通して測った（曲がりの揺れ = 細かく刻んだ曲線の、隣り合う区間の向きの変化の中央値 / 90%。
元へのずれ = 生の点から曲線までの距離。体の高さ = 1 の %）。

| 作り方 | 報告の動画 曲がり | 同 ずれ | macroy 曲がり | 同 ずれ |
| --- | --- | --- | --- | --- |
| **いま**（SG5 ×1 → 採る → **点を通る**曲線） | 2.47° / 9.29° | 0.60 / 1.72 | 1.99° / 10.87° | 0.29 / 2.19 |
| SG5 ×1 → 平均で間引き → 点を通る曲線（§6） | 2.22° / 7.72° | 0.62 / 1.71 | 1.55° / 8.21° | 0.36 / 1.97 |
| **SG5 ×1 → 採る → 点の近くを通る曲線** | **1.74° / 4.48°** | 0.78 / 2.63 | **1.14° / 5.29°** | 0.43 / 2.52 |
| SG5 ×1 → 平均 → 点の近くを通る曲線 | 1.48° / 4.03° | 0.87 / 2.53 | 0.87° / 4.66° | 0.46 / 2.83 |
| Whittaker λ=1 → 採る → 点を通る曲線 | 2.21° / 7.10° | 0.64 / 1.76 | 1.50° / 6.91° | 0.34 / 1.85 |
| **Whittaker λ=10 → 採る → 点を通る曲線** | **1.45° / 4.14°** | 0.90 / 2.48 | **0.87° / 5.12°** | 0.44 / 2.62 |
| Whittaker λ=100 → 採る → 点を通る曲線 | 0.88° / 2.23° | 1.04 / 3.10 | 0.44° / 2.58° | 0.53 / 3.50 |
| Whittaker λ=10 → 採る → 点の近くを通る曲線 | 1.22° / 2.86° | 0.99 / 3.25 | 0.67° / 4.10° | 0.46 / 3.24 |

### 案 A：描く曲線を「点を通る」から「点の近くを通る」に変える

いまは Catmull–Rom で、**すべての点を必ず通る**。測定点にブレが乗っていれば、曲線は定義上そこを通らされるので、
ブレがそのまま角として出る。これを一様 3 次 B スプライン（点を制御点として扱い、通過はしない）に替えると、
**曲がりの揺れが 3 割減り、90% 値は半分になる**（2.47 → 1.74、9.29 → 4.48）。
代償は元の点からのずれが 0.60 → 0.78（体の高さの %。画面で 0.5pt 程度）。

- 変更は `JointTrailOverlay.curve(through:)` のベジェ制御点の式だけ（一様 3 次 B スプライン → ベジェの変換は 4 行）。
  保存データも形式の版も変えない
- 曲線の端が制御点まで届かないので、線の始まりと終わりを合わせる処理（端の制御点を 2 回置く）が要る

### 案 B：Whittaker（罰則付き）平滑化で曲線を当てはめる

「観測との差の 2 乗」＋「λ ×（2 階差の 2 乗）」を最小にする点列を解く。**運動が急に折れ曲がらないという前提を式にしたもの**で、
窓の幅ではなく λ 1 つで滑らかさを決める。λ=10 で曲がりの揺れは 2.47 → 1.45（SG を 3 回掛けるより効く）。

- **欠けたコマを自然に埋める**（重み 0 で解けば、前後から滑らかに補間される）。いまは 0.3 秒までの欠けを直線で結んでいる
- **信頼度で重み付けできる**。Vision は関節ごとに信頼度を返すのに、いまは 0.3 で足切りして残りは同じ重みで扱っている。
  ぼけたコマを軽く扱えば、外れ値に引かれなくなる
- カルマン平滑化（前向きフィルタ + 後ろ向き RTS）で「等加速度＋過程雑音」を仮定するのと**同じ族**で、
  2 階差の罰則はそのまま「加速度が急に変わらない」に対応する。実装は Whittaker の方が短い（連立方程式 1 つ）
- 解くのは 5 重対角の連立方程式で、点数に比例した手間で解ける（調査ではガウス・ザイデル法で代用した）

### 組み合わせ

案 A と案 B は独立で、両方だと 2.47 → 1.22（90% 値は 9.29 → 2.86）。ずれは 0.99 とまだ体の高さの 1% 以内。
見た目の比較は `build/curve-compare.png`（左からいま / B スプライン / Whittaker λ=10 + B スプライン。人物が写るので docs には置かない）。

### 他に考えた案

- **解析レートを上げる**（240fps 原本を 30 → 60fps で解析）：点が倍になり平均が効くが、Vision の実行が倍になる
- **制御点を少なくして最小二乗で当てはめる**（B スプライン近似）：案 A をさらに進めた形。80 点の制御点で足りているので、いまは不要
- **極座標の多項式**（クラブヘッドで試した Gehrig らの方法）：手の軌跡は 1 本の多項式で書ける形ではないので合わない

## 9. 頭を消す（TODO L の 2）

平滑化とは独立の作業。`BodyPart.head` と `JointTrailSample.head`、`PoseTracker.headLocation`（鼻 → 目 → 耳の代用）、
`BodyPart+Color` の色、`PoseFrame.head` を消し、`JointTrails.currentVersion` を 2 に上げれば既存の軌跡は開いたときに作り直される。
色は 5 本になるので、頭に割り当てていた青（色相 0.60）が空く。

## 11. 計測ツール

`build/smoothcheck`（ソースは scratchpad。`SwingDuet/Services` の解析一式と `Models` を一緒にビルドする）。
`build/smoothcheck <動画>...` で、部位ごとに候補 8 つの「振動・元からのずれ・遅れ・トップとインパクト付近のずれ・道のり比」と、
検出側に掛けた場合のフェーズを出す。

`build/curvecheck <動画>... [--draw <出力 PNG>]`（§7 用）。平滑化 → 間引き → 曲線の作り方を通しで組み合わせ、
**画面に出る曲線**の「曲がりの揺れ（度）」と「生の点からのずれ」を測る。`--draw` で 3 通りを並べた画像を書く。

## 12. 部位ごとに強さを変える（実機での指摘を受けた追試）

案 A（B スプライン）を実機で見たところ「手はよくなったが、**頭と両股関節の振動が強い**」という指摘。測ると数字も一致した
（マキロイの動画、**描く曲線**の曲がりの揺れの中央値）：

| 部位 | 動いた道のり | いま（SG5 ×1） | 適応平均 |
| --- | --- | --- | --- |
| 手 | 1053 | 2.03° | 0.85° |
| 頭 | 582 | **4.02°** | 2.70° |
| 左肩 | 801 | 2.07° | 1.23° |
| 左股関節 | 428 | **3.12°** | 1.70° |

**ほとんど動かない部位ほど悪い。** 線に占める「本当の動き」が小さく、残ったブレの割合が大きいため。手は弧が大きいので、
同じ大きさのブレでも向きの変化が小さく見える。

平滑化の効き方も部位で違う。手のように弧を持つ部位は Savitzky–Golay（2 次多項式の当てはめ）が形を残すが、
**ほとんど動かない部位ではその「形を残す」性質が仇になり、ブレを残してしまう**。単純な移動平均の方が落ちる。
